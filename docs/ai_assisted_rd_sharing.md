# 用 Agent 做论文阅读与复现：从 25 篇论文到 97.86% 的工程流程

> 用途：15 分钟分享。素材来自一个真实研发项目（论文驱动实现，80+ 版本迭代，
> session 准确率 84.19% → 97.86%），方法已沉淀为可复用的 skill。
> 所有结论均有实验记录背书（证据指针见附录）。
>
> **时间分配**：开场 1min / 总览 1min / 论文详读 3min / baseline 2min /
> 消融循环 3min / 错误分析+两条红线 3min / 归档与工具化 1.5min / 收尾 0.5min

---

## 0. 开场：这个场景难在哪（1min）

今天讲一个非常具体的场景：**手里有一个在研项目，如何用 agent 读一批论文、把论文里的机制复现进现有代码**。

注意这不是"独立复现论文"，区别很大：

- 你有**现有代码**——论文组件要判断"替换还是旁路"，不是从零写；
- 你有**现有数据和评估口径**——论文的数字口径和你的口径多半不一致，不能直接对表；
- 你有**现有瓶颈**——论文 10 个组件，可能只有 2 个对症，其余 8 个复现了也是负资产。

所以这个场景的核心问题不是"agent 能不能读懂论文"，而是：**如何管住 agent，让它读得有判断、复现得可回退、结论可复算**。

一句话结论先给：**agent 负责"读全部、写初稿、跑回归、记档案"，人负责"前提判断、采纳闸门、扼杀方向"**——下面每个环节都会落到这个分工上。

---

## 1. 总览：五阶段流程（1min）

```
0 论文详读 → 1 baseline 跑通 → 2 消融循环(×N) → 3 错误分析 → 4 归档汇报
                ↑____________|____________↓
                （消融循环内嵌错误分析）
```

四条核心纪律贯穿全程：**基线先行、单变量消融、口径诚实、失败入档**。

这个流程不是设计出来的，是 80+ 版本迭代踩坑收敛出来的。下面逐阶段讲 agent 怎么用、坑在哪。

---

## 2. 阶段 0：论文详读——别让 agent 只"总结论文"（3min）

### 2.1 组织方式：先建论文库，再逐篇详读

我们的做法：25 篇相关论文按方向分 A/B/C/D/E 五类，每篇由 agent 产出一份**结构化详读笔记**入库。关键不在"读了"，而在笔记的模板——模板决定了 agent 的输出是"读后感"还是"工程决策依据"。

模板里最关键的字段是**方法拆解表 + 采纳判断表**：

| 组件 | 做法 | 论文报告的收益 | → | 判断 | 依据 |
|---|---|---|---|---|---|
| 组件1 | … | … | → | ✅采纳 | 对症哪个瓶颈？预期收益？ |
| 组件2 | … | … | → | ❌不适用 | 场景假设不匹配的具体点 |
| 组件3 | … | … | → | ⏳待验证 | 缺什么信息？怎么低成本验证？ |

**硬性要求：每个组件三选一，依据必填，写"为什么"，不许写结论套话。**

### 2.2 实证：三选一是怎么发挥作用的

以一篇对话状态跟踪论文（S3-DST）为例，agent 详读后的判断：

- **PAR 机制 ✅采纳**——对症我们当时的 record 指代瓶颈，后来确实带来收益；
- **segmentation ❌不适用**——论文假设长 multi-topic 会话，我们是 task-oriented 短会话，场景前提不成立；
- **XML 输出格式 ❌不优于现有 Text-to-Python**——不是拍脑袋，做了小规模实证对比。

**"不适用"的判断和"采纳"一样值钱**——它防止后来人（包括下一个会话的 agent 自己）重走死路。我们的失败模式库里有多条路线，都是"尝试 2 次净负后永久封死"，这些判断全留了档。

### 2.3 调研类任务：要求 agent 逐篇核实原始出处

批量调研时不要只要"总结"，要明确要求 agent **逐篇核实 arXiv 编号、机制描述、量化结论**。一次路由方案调研中，这个动作抓出了 2 个流传资料里的错误编号（一篇组合优化论文被误当 cascade 论文引用）——二手综述里的错误会直接污染方案取舍。

**人的拦截点**：agent 的论文→机制映射速度快，但会"创造性发挥"。关键公式、关键流程、关键数字，必须人对照原文抽检。

## 3. 阶段 1：baseline 先行——锚点不立，后面全是虚的（2min）

纪律三条：

1. **先跑最小可复现版本**（v1.0），不做任何论文外的创新。agent 天然想"顺手优化"，要摁住。
2. **固定评估脚本和 split，此后所有版本同一口径**。口径换了必须重跑 baseline 对齐，禁止跨口径比数字。
3. **论文多组件时，baseline 后立刻做 on/off 消融**。我们做过检索 on/off = 68%/60%，确认 +8pp 是真实收益才继续深入；反过来，PMI 重排组件消融无收益，及时删了——**无效组件留在系统里就是多出来的变量**。

为什么强调锚点：后面几十版迭代里，±2pp 是噪声带。没有同口径锚点，agent 提交的每个"提升"都无法证伪。

---

## 4. 阶段 2：消融循环——六条纪律管住 agent（3min）

这是核心阶段，agent 在这里发挥最大执行力，也最需要刹车。每个版本迭代六条，**缺一步等于没做**：

| # | 纪律 | 管什么 |
|---|---|---|
| 1 | **config 开关控制改动**，默认关闭 | 秒级回退；大改动先旁路实现、全量回归证明无副作用再开开关 |
| 2 | **单变量**：一版只改一件事 | 多变量混合实验无法归因（真实教训：一版改 3 件事，回退时把有效组件一起杀了） |
| 3 | **全量重跑**，不跑子集 | 子集结论经常被全量推翻 |
| 4 | **跑完即做错误分析** | 不看错误样本就改下一版 = 盲人摸象（下节展开） |
| 5 | **CHANGELOG 固定字段入档**：动机/改动/数字对比/根因/教训 | 跨会话连续性 |
| 6 | **净负如实回退**，不美化数字 | 失败版本的"勿再走此路线"是最值钱的资产 |

**采纳闸门上两道锁（人把持）：**

- **双跑 + 噪声带**：±2pp 内的"提升"不是提升，采纳必双跑。agent 的论证再有说服力，也要先过数字闸门——实测最有说服力的一份方案（论证链完整、文献充分），oracle 上限实验一做，**上限仅 +1.63pp，整条路线关闭**，省了至少两周无效开发。
- **翻转归因**：每次改动统计"稳定获救/稳定回退"样本并逐个核验，区分机制因果 vs 运行波动。

## 5. 阶段 3 + 两条红线：错误分析与评估口径（3min）

### 5.1 错误分析：agent 的数量级杠杆点

做法：按**错误类别**归因（漏意图/指代/时间推算/值错误/格式错误），不按个案归因；产出可视化报告（对话原文 + GT vs pred 差异 + 逐样本归因，HTML 单文件）；下一版优先级按**类别占比 × 可修复性**定，不按"最近看到的那个 bad case"定。

agent 在这里是数量级杠杆：65 个失败 session，每个含多轮对话+模型原始输出+GT 对照，人通读要一天，agent 一小时产出 9 类机制归因报告（含占比、代表样本、修复建议）。**但归因结论影响方向，人要抽查。**

### 5.2 红线 1：评估口径纪律（动手前必读）

口径不诚实，后面所有数字都是垃圾。三条血泪：

- **真实透传**：多轮任务上一轮用模型真实输出，不用 GT 喂回去。真实案例：GT 透传口径 70.5%，换真实透传暴跌到 58%——**乐观口径下做的所有版本对比可能全部失真**。
- **先查数据集噪声，再调模型**：某类场景长期低分，各种 prompt 调优无效；最后发现 GT 标注规则与模型可见信息不一致（生成器取第 1 条 vs harness 展示最近在前），模型按任何合理规则都必错。写脚本做噪声扫描，49/352 = 13.9% 的 test 是这类噪声，剔除后 55.97% → 62.71%。
- **剔除口径与全集口径并列报告**，不只报好看的那个；报数字必带分母。

### 5.3 红线 2：失败模式库（F1–F9）

我们把净负实验沉淀成 9 条失败模式，agent 动手前必过一遍。举三条最有迁移价值的：

- **F1 demo 注入格式不一致是负资产**：注入的 few-shot demo 缺一个结构头，模型模仿省略 → 下游解析失败 → 整段输出被丢弃。同一项目**复发了 3 次**。教训：先看 demo 格式与目标格式逐标记对齐，再谈内容质量；注入后验证"格式合规率"。
- **F2 生成侧的问题在生成侧解决**：后处理选择器/补全器在 validate 之后二次干预，两次尝试（v5、v9）均净负后**永久封死**，转向把推理链注入 prompt 的生成侧方案——首次显著超越基线。
- **F6 信息不对称**：某类需要上下文的场景长期 0 分，根因是关键信息根本没进 prompt（agent 的话术轮没喂给模型）。排查口诀：**"人类能做对、模型 0 分"的场景，先核对模型输入里到底有没有必需信息**。补上信息通道后 0/18 → 3/18 并带来 +3.3pp 广谱收益。

**注意 F1/F2 的共性：agent 不会主动放弃自己的方案。** 两个月里所有"封死"决策都来自人。对策：把封死清单写进档案，要求 agent 每次提案前自查——用 agent 的文档执行力对冲 agent 的方案惯性。

---

## 6. 阶段 4：归档汇报与工具化（1.5min）

### 6.1 三册归档

每次实验后三件套：重跑 + 错误归因报告 + CHANGELOG 归档，缺一不算完。最终沉淀三册：

- `report.md` 总览册：一页——当前最佳数字、导航、复现命令；
- `report_method.md` 方案册：论文依据与采纳判断、方法演进表、失败教训、config 开关清单；
- `report_experiments.md` 实验册：全版本结果总表、错误分类分析、瓶颈与上限。

价值不在"有文档"，在于**跨会话续接无损**：两个月后新会话读档即恢复全部上下文，agent 不重复提议死路。

### 6.2 工具化：整套流程沉淀为 skill

上面全部内容已固化成一个 Claude Code skill（`paper-reproduce`）：五阶段流程 + 5 个模板（论文详读/CHANGELOG/三册报告）+ 3 份 reference（评估口径清单/失败模式库/错误分类法）。模板即纪律——**把人的拦截点写进 agent 的默认输出结构里**，比每次口头叮嘱可靠得多。

---

## 7. 收尾：带走即用的清单（0.5min）

**读论文阶段**
- [ ] 建论文库，详读笔记用"组件拆解 + 采纳三选一 + 依据必填"模板
- [ ] 批量调研要求 agent 逐篇核实原始出处
- [ ] 人抽检关键公式/数字，防"创造性发挥"

**复现阶段**
- [ ] baseline 先行，固定口径和 split；多组件立刻 on/off 消融
- [ ] 消融循环六条：开关化 / 单变量 / 全量重跑 / 跑完即归因 / CHANGELOG / 净负如实回退
- [ ] 采纳双闸门：双跑+噪声带、翻转归因——agent 说服力不进采纳决策

**纪律红线**
- [ ] 真实透传、先查数据噪声、口径并列报告、数字带分母
- [ ] 失败模式入库，封死清单要求 agent 提案前自查

**一句话**：论文复现的瓶颈从来不是"读不懂论文"，而是**前提判断和采纳纪律**——这恰恰是人最不该外包给 agent 的部分。
