# 11 时间规则：预计算注入 vs 后处理 vs LLM 改写

> 来源：v23（时间规则后处理净负回退）、v23.3（弱模型假设证伪）、v27.0（预计算注入采纳定案：**session 92.74% / turn 93.54% / 状态机 86.08%，+4.71pp/+3.64pp，time_wrong 19→5**；含 run1 81.20% −6.8pp 大回退与两轮修复全过程）
> 本篇是 50+ 版本里"同一问题三次尝试、前两次全败、第三次大赢"的完整解剖，重点在**为什么第三次赢**。

## 1. 三种形态的判决（附否决证据）

用户直觉最自然的两种方案都失败了，第三种才成功：

| 形态 | 思路 | 结果 | 否决根因 |
|---|---|---|---|
| A. 规则后处理 | 提取时间→改 pred / 与 pred 对比纠错 | v23 净负（回放 1修0破恒等失效） | ①模型输出已规范，规则无信息增量；②GT 口径本身反规范化（矛盾保字面、OCR 保字面），把 pred 改"合理"只会离 GT 更远；③validate 后二次干预连带破坏（v9.0 同教训） |
| B. LLM 改写轮 | 先让模型把时间改写成规范格式再进 DST | 未跑即否决 | 改写器与 DST 共享同一日期算术弱点，误差只是上移；每轮多一次调用；改写改变话语分布影响检索 |
| C. 规则提取+预解析+prompt 注入 | 规则算好结论，模型引用结论 | **v27.0 +4.71pp** | ——（与 record_rule/candidate_map/pending_app_rule 全部成功改动同构） |

**判据（可迁移）**：先问"这个环节需要的是理解还是计算"。计算（日期算术、格式转换）→ 规则做，结论喂给模型；理解（哪句话对应哪个意图、该不该落槽）→ 模型做。**把计算塞给模型是浪费（见 §4 论文依据），把理解塞给规则是 v23 的错误**。

## 2. 六类时间错误与对症（v27.0 错误归类，d6 实测）

| 形态 | 例 | 对症 | 命中 |
|---|---|---|---|
| 相对日期 off-by-one | "后天"算成+3天 | TIME ANCHOR 预计算日期表（今天/明天/后天/大后天+星期），查表禁止推算 | S-000119/249 |
| 明说时间被 record 覆盖 | "后天凌晨1点半结束"但模型抄 record 时间 | 提取器给出明说候选 + TIME RULE（明说>record） | S-000140 |
| 矛盾口径被调和 | GT 保字面 start>end，模型自行翻转 | 矛盾检测（确定性）→ 注入"保字面勿调和" | S-000066/227（start/end 治好；duration 为 GT 设计字段不可达） |
| 画像时段 vs 时长冲突 | profile "10:00-12:00" vs "90min" | 检测不一致 → 注入"以时段为准" | S-000063/165/237 |
| 候选未定落槽 | "还没定，A 或者 B" | 候选邻接标记 → 注入"候选不落槽只记无歧义字段" | S-000185 |
| 区间终点省略时段词 | "晚上7点到8点半"的"8点半" | （修复后）子句级时段继承 | 全 d6 高频形态 |

## 3. run1 −6.8pp 大回退的解剖（本项目单次最大回退，教训密度最高）

- **根因只有一个**：区间终点省略时段词。"明天晚上7点到**8点半**"——"8点半"是裸时刻，初版提取器解析成 08:30（GT=20:30）。该形态在 d6 是主力句式，30 个 session 破窗全部同型。
- **二级伤害来自规则间的交互**：错误预解析触发 start>end → 矛盾规则"照字面录入"生效 → 模型忠实抄下错误值。**每条规则都在为其他规则的错误背书**——注入类机制的错误不是加性的，是乘性的。
- **回放没拦住的原因**：对照组 12 个里 base 自身在 S-000005 有 time_wrong 0→1 的增量信号，但回放只看 session 翻转，被 base 波动掩盖。**纪律补丁：回放对照必须盯 turn 级机制桶（time_wrong）增量，不能只看 session 级翻转**。
- **为什么首轮全量前没发现**：宁缺毋滥的原则管住了"不解析"的一侧（放弃模糊候选），没管住"解析错"的一侧。**提取器的失败模式不是漏，是错的自信**——回放集必须覆盖目标 case 之外的高频句式（本例：区间省略时段词在 11 个目标 case 里只有 2 个）。

## 4. 论文依据（arXiv 2026-09-20 检索，为什么"给预计算结果"是对的）

- **arXiv:2505.16088**（Date Fragments）：日期错误部分源于 BPE 分词割裂，不常见日期掉点达 10pp——模型"懂规则但算错"有分词层机制解释，prompt 文字规则救不了。
- **arXiv:2601.07148**（Time Puzzles）：GPT-5 无工具 55.3%；**显式给日期时性能显著提升**——直接支持预计算日期表。
- **arXiv:2511.09993**（SPAN）：LLM 跨历法平均 34.5%，工具增强代码生成 agent 95.31%——时间计算交确定性代码。
- **arXiv:2507.06450**：时间归一化 = LLM 代码生成 + 可执行校验框架（规则做算、LLM 做理解的同构）。
- **arXiv:2505.20243**（It's High Time, ACL 2026 综述）：窄域时间归一化规则系统（SUTime/HeidelTime/Duckling）仍是基线强度。

## 5. 工程要点 checklist（复刻本机制时逐条过）

1. **六开关独立消融**（日期表/证据/四条口径规则各一个 config 键），回退路径始终存在。
2. **prompt 净长度对冲**：加日期表同时压缩旧时间散文段（9924→9084 字符），把"变长税"变成净减。
3. **提取器宁缺毋滥**：解析不确定→不产出→prompt 与现状逐字节一致；全量扫描提取值 vs GT 一致率 99.4% 才放行。
4. **注入形态只给证据和规则，不给答案**：TIME EVIDENCE 列候选+[start]/[end] 角色，绑定归属留给模型——多意图句（8 个 mention）组装反而会错。
5. **矛盾规则要防误触发**：矛盾检测必须是确定性的（提取器已解析三值比大小），且与跨夜滚动互斥（合法解读优先于矛盾判定）。
6. **时段继承按子句级**：混合时段句（"晚上7点到8点…上午6点到9点"）第二段跟上午，不跟句级主导时段。
7. **时长候选与时段候选分开**："选三个半小时还是三个小时"只抑制时长断言，不抑制 start/end（GT 口径时长悬空但时段明说）。
8. **目标 case 回放（1修0破）+ 高频句式回放（防错的自信）+ 对照组 turn 级机制桶增量**，三关都过才进全量。

## 6. 增补（v27.1，2026-09-23）：注入的另一条边界——不要对抗已验证的行为面

record_selector 三轮全量否定（81.20/88.46/89.32% vs v27.0 92.74%）补完了本篇的第 5 条 checklist 之外的新教训：

1. **注入会与既有已验证机制竞争行为面**。record_rule（+4.97pp）的"取 records[0]"行为是模型已稳定习得的；v27.1 的定位类 EVIDENCE 用不同措辞描述同一件事，模型的遵从模式被重排——13 个原本判对的 session 破窗（rtt=None/画质=None 型）。**同一语义的第二种说法不是冗余备份，是行为面扰动源**。
2. **暴露决策过程细节会诱导模型重算**。EVIDENCE 写"约束命中 6 条"后，模型开始自行按 service 过滤换记录（S-000005 summary 实证原文）；改为只给结论（上次记录=明细）才收敛。**给结论时不要附带模型的"思考素材"**。
3. **口径冲突必须显式压制散文规则**。系统 prompt 的【记录选择规则】教"过滤后取最近"，与悬空规则正面冲突——defer 提示必须写"本条覆盖一般规则"，且散文侧要加例外行，否则模型择亲近者从之（S-000123 t1 实证）。
4. **靶区有效的机制也可能整体净负**。defer 在 T3-3 家族 5 例机制性转正（含消歧补值链条端到端工作），但非目标类扰动 13 例——判定标准始终是净效应而非靶区命中率。

对照第 1 节的形态判决表：时间机制成功是因为它注入的是模型**行为面之外的新信息**（预计算日期表），record 失败是因为它试图**改写模型已稳定习得的取值行为**。两者的分界线即本条教训。

## 7. 增补（v27.2.1，2026-09-24）：表遵从波动的治法——条目高亮而非改表

"高清@淘宝/看直播=1080p"是反常识条目（高清>标清720p），模型倾向落全局默认 720p——三个 session 稳定错在同处，且基线复跑同样错。核对后 prompt 表与标准表 diff=0，**错不在表而在遵从**。修复 = QUALITY HINT：话语提及 app/画质词时，把标准表对应条目以独立段落放大注入（schema.QUALITY_MAP 79 条常量，全 case 平等不挑反常识），5/5 定点验证转正。

两条补充教训：
1. **先核对表，再修遵从**：出错时第一个直觉是"表错了"，实际 diff=0——如果直接改表会引入数据泄漏且破坏数据侧单源。
2. **"放大要看的行"属于顺行为面的注入**：与 v27.1 失败的定位类注入不同，QUALITY HINT 不与任何已验证机制竞争——它只是把系统 prompt 里已有表格的对应行在 task prompt 里再强调一次，模型查表行为本来就存在（时对时错），高亮是提高信噪比而非改变行为模式。

## 8. 增补（v28.2/v28.3，2026-10-20）：抑制类规则的"限定对象"判定与"文案同步"纪律（d930 泛化攻坚）

**背景**：d930 新一代泛化集 65 例错误报告中 T2 类（16 例,25%）为最大类——"应用和时延还没定，明天晚上11点到后天凌晨1点"型话语，已明说完整的时间被整体抑制（组装清空+TIME RULE"一律留空"），t2 澄清后明说时间永久丢失。d6 时代未暴露：d6 话语的未定词都真实限定时间。

**根因双层**：
1. **extractor 层**：`_generic_undecided` 的槽位白名单只有"(开始|结束|截止)时间"前缀——"应用和时延还没定"/"时长我还没定"/"时延上限30ms，我还没定"（值插中间）全部误判为全局未定。修法 = 关键词扩展（应用/时延/时长/画质/分辨率/清晰度/走/选）+ 三层限定形态：紧邻（≤6字）/隔值（6~16字且关键词与未定词间无标点——值插中间形态）/后向选项列举（"…我还没定，是1080p配时延上限…"带"是…配"形态）+ app 名命中（"是云视讯…还是Telegram…还没定"）。
2. **prompt 层**：extractor 修好后 TIME EVIDENCE 组装成功，但 TIME RULE 旧文案"start/end 一律留空"仍把组装结论压掉（模型 summary 原话"受TIME RULE约束，start/end留空"）。修法 = TIME RULE 文案随组装结果分叉：组装成功→"时间本体已明说,照常落地,未定的只是其他槽位"；时间本身二选一→保留"留空"（S-000185 真候选时段语义经隔值标点校验+"是…配"形态校验保持抑制）。

**结果**：s444 94.72%（+0.91pp）、s444b 94.48%、合并 871 抽样定案 94.60%/95.07%；T2 类 16→3。

**教训（抑制类规则通则）**：
1. **抑制类规则（"XX一律留空/不落槽"）必须有精确的限定对象判定**——未定词的语义指向要看它限定的槽位（限定 app ≠ 限定时间），且形态覆盖紧邻/隔值/后向三种。新数据集的话术变化会让"宁缺毋滥"的抑制变成黑洞。
2. **修 extractor 必须同步修下游 prompt 文案**——证据组装放行了，下游规则文案还在说"留空"，等于没修（v28.2→v28.3 一轮纯粹为此买单）。工程纪律：任何"提取器/规则"改动，grep 所有引用其结论的 prompt 段落，逐一核对语义一致性。
3. 抑制类文案要写成**条件式**而非绝对式："时间本体已明说→落地；时间本身未定→留空"，让规则自洽覆盖两种形态，而不是靠 extractor 侧"不给证据"来隐式豁免。
