# 07 数据集工程：标注缺陷的甄别与"设计口径"的边界

> 来源：v6.0（噪声三路扫描 0 结论）、v19（R5 重扫 13 条）、X-2 slot_updates 缺陷（22 session）、d5 invalid_resolution_unit 场景、T3-3 表达式设计

## 1. 甄别"标注缺陷 vs 模型错误"的标准流程

1. **先证伪评估代码**：怀疑 GT 错之前，先确认 eval 的 GT 构建逻辑无 bug（S-000082 案例：先排除了 error_report/JGA 提取错误，才指向标注）。
2. **扫描全量找模式**：单例怀疑无意义，写扫描器找"同值同名字段在取消兄弟意图上登记更早"这类结构性模式（X-2 22 session 一网打尽）。
3. **找反例甄别**：同模式命中的不一定全是缺陷——T2-6 的 29 个同模式命中全是误报（轮1 确实没说，轮2 才首次陈述，GT 正确）。**每个命中都要人工回到话语逐字核验**。
4. **区分三种性质**：
   - 标注缺陷（X-2 duration 延迟登记）→ 修数据或评估口径豁免；
   - 设计口径（T3-3 话语不复述 app、invalid_resolution_unit 记字面值）→ 评估侧豁免/标记，不动数据；
   - 模型错误（超前补齐、知二推一抢跑）→ 生成侧解决。
   **三者混判是错误归因最大的坑**——v24.1 时代 missed_intent 被"归因能力短板"，实为 key 断裂假象。

## 2. 生成器与评估的一致性前提

- R5 噪声的根因：生成器把"上次"绑到 records 原始顺序第一条，而评估/模型看到的是 completed_at 降序——**生成器与消费端的顺序约定不一致，规则一变噪声就变**。数据集版本升级必须重扫噪声。
- 共享子句绑定：模板里"时间都是X"这种跨意图子句，生成器只绑给部分意图（将被取消的），存活意图延迟登记——**evidence binding 必须覆盖所有被话语覆盖的意图**，否则 turn 级评估出现系统性假错误。

## 3. "设计口径"的判定与豁免

- T3-3"就选第一条"场景：话语本不复述 app/service（值来自画像记录）——评估时 missed_intent 里 app 来源是 Record 的要标注"设计如此"。
- 用户说错更正（invalid_resolution_unit："1080m"→自纠"1080p"）：GT 轮1 记字面错误值是**故意设计的对话现象**，评估侧豁免（v20.2 correction_credit）而非改数据。
- 判据：**这个"错误"是否在测试系统的特定能力？** 是 → 设计口径，豁免；否 → 标注缺陷，修。

## 4. 数据集版本管理

- 每版规模/模板分布/ID 重叠/谱系入 docs/dataset_versions.md（变更时必须更新）；
- 换版本 = 重建 split/casebank/embed cache/画质映射表（从 train source_ref 还原规范表 v20.0 +2.17pp）+ 重扫噪声 + 旧口径数字作废标注；
- 用户画像（users.jsonl）与 session 分开存放，record 顺序约定（completed_at 降序=模型所见）要写进文档。

## 5. 从数据反推系统短板

模板即测试维度：T1-1 直接/T1-2 域外/T1-3 多意图/T1-4 记忆复用；T2-1 补槽/2 澄清/3 冲突/4 追加/5 改参/6 取消；T3-1 确认/2 更正/3 消歧/4 结束；X 混合编排。
**按模板分桶的准确率是系统能力画像**：T3-3 长期 0/14 暴露信息不对称（后由 agent_context 解决）、T2-1 集中暴露补槽 key 断裂（后由 v25.2/v26 解决）。数据集的模板设计本身就是错误分类学。

## 增补（v26.3，2026-09-15）：模板分布放大隐含架构假设

dataset_6 的 T1-3（单轮同头多档位）和 T2-6（同头双意图取消）把"同 app+service 多意图"从 d5 的 2/819 稀有场景放大到 6/237——**系统的 dict 键唯一假设立刻崩塌**（session_gt/pred 透传/状态机/报告四处塌缩）。两点泛化结论：
1. **新数据集的模板分布变化本身就是对系统隐含假设的压力测试**。跨数据集评估的价值不只是"泛化性分数"，更是暴露旧数据集里被稀有度掩盖的结构缺陷；d6 上 T3-3 消歧洼地（candidate_map +2.99pp 转正）与同 key 塌缩（P3 实例化）两个发现都属此类。
2. **同 id 双份不同渲染（id 冲突）是新批次的常见坑**：438 行中 201 id 各有两份完全不同对话，去重策略（render_meta 优先含质检软通过）要在建库时一次性定清楚，否则 train/test 泄漏与重复计分都会静默发生。
