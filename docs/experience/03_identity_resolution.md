# 03 引用解析/意图身份：本项目最贵的一课

> 来源：v25.2（harness 对象语义 +6.52pp）、v26.0（裸 id 协议 −3.11pp）、v26.1/2/2b（补丁链转正 88.67%）、v12.1（demo 补头）、v9.0（选择器失败）

## 1. 问题本质

增量式 DST（每轮输出 Δy）里，"这是哪个意图"的身份判断必须有人做。谁做、用什么做，决定了三类经典病灶的出现概率：

| 病灶 | 症状 | 实测损失 |
|---|---|---|
| 改口裂 key | 只改 app 时 key 丢 svc（爱奇艺/看直播→爱奇艺），旧 key 残留幻影 | v24.1 时代 26 个 session 带幻影 |
| 补槽并存 | prev 挂残缺头（'/视频'/'none'），补全轮匹配不到 → 同一意图两份状态 | S-000850/183/263 型 |
| 取消错位 | 同 app 双意图时按名字归一化取消错对象 | T2-6 型低频但致命 |

## 2. 责任分配的最终答案：三层混合

**模型层（显式指派）**：改口/多意图更新/消歧选择——话语有明确目标信号的场景，模型可靠。id 比名字省 token（不用复述 app/svc），名字比 id 自校验。
**harness 层（推断指派）**：补全型共指——残缺意图补 app、"改配置"轮模型犹豫写 new。模型在"更新还是新建"上不可靠（v26.0 裸协议实测），必须确定性规则兜底：
- 归并校验两级信号：无 app 同 svc 唯一（强）/ 唯一无 app 悬置意图（弱）；
- full-match 重采样门：new 段产出与 prev 意图完全同名且话语无新增词 → 提示后重采样（full-match 安全：全库同 app+svc 双意图仅 2 例）。
**审查层（全场去重）**：同轮多段产出同 key 时段间覆盖——dict 后写覆盖先写会静默吞掉正确输出（S-000040 现场：I1 段完全正确被冗余 new 段盖掉）。这类 bug 只有翻转归因能抓到。

## 3. 身份判定的收益在"强制写理由"，不在"换介质"

- 身份判定强制化（段头前必须写 `# 身份判定: ...` 一行，PAR 校验不过重采样）：救回 new 重建型错误（S-000040/845/935/325），代价是每段 +1 行 prompt 税（15 个 v25.2 稳对翻成波动）。
- 这与 v11 选择链（record 选择强制写推理，+2.87pp）同构：**PAR（生成前显式推理）的价值 = 逼模型先看可用选项再做决定**。
- 但写 `# 身份判定` 行本身有博弈面：模型会写出正确理由却得出错误结论（S-000040 v26.2 现场："I1 是京东视频…故京东视频为 new"）——判定行提高认知门槛但不保证结论，真正的保证是 harness 去重兜底。

## 4. 失败形态库（这些路不要走）

1. **后处理选值/投票/重注入**（v5.0/v9.0/v24.5）：只补缺失不覆盖保护不住重新 validate 的连带破坏；翻转值是多稳定吸引子竞争，投票选出的是贪婪已选的吸引子。oracle pass@2 仅 +1.63pp，上限锁死。
2. **裸 id 协议无兜底**（v26.0）：遵从率 100% 但语义错误依旧——形式遵从 ≠ 语义正确，协议实验必须看语义翻转。
3. **id 用于 cancel**：分配序与模型心智模型错位（模型以为 I1 是它想取消的那个），且错位无法从格式识别。cancel 场景名字引用自带语义、写错立刻可见。
4. **key 从 delta 推导**（v25.2 之前的默认）：改口单字段必裂 key。key 应从合并后 final_state 推导（对象状态=prev+delta 合并，规范名从当前内容导出）。

## 5. 与对象化架构的关系

彻底的对象化（模型程序里直接引用 `intents[I1]`）理论更干净，但代价是：沙箱/校验器/coreference 全链重写 + demo 库全量重渲染 + 模型学习成本。本项目的经验：**薄映射层（id↔内容 key 双向账本 + 段头路由查表）+ 三层兜底**，以 ~10% 的改动量拿到对象语义的主要收益——先做薄的，数据说话后再决定要不要厚的。

## 6. v26.3 增补：实例化 key 与触发式规则的边界（2026-09-15）

### 6.1 同 key 多意图：塌缩是 dict 架构的系统性盲区

intent_key = app/svc 贯穿 GT/pred/状态机全链时，**任何"按 key 建 dict"的地方都会在同 key 双意图上塌缩**——本项目实测暴露四处：session_gt、pred 透传、状态机两侧、error_report source_map。更隐蔽的是**塌缩产生假阴性**（两条 GT 塌成一条后恰好与 pred 相等 → session 判对），错误被系统性掩盖多个版本，直到逐例核查 error html 才发现。**教训：评估口径里"dict 键唯一"是一个隐含假设，换数据集/换模板分布时必须显式验证它**（d6 的 T1-3 同头多档位模板把 d5 时代 2 例的稀有场景放大到 6/234）。

### 6.2 实例化分层的落地形态

`app/svc#N` 后缀只存在于 harness 内部（模型只见 I1/I2，id 协议天然唯一）；GT 侧锚点用数据集现成的 intent_id（编号基于全量 intents 含 cancelled 的出现序——cancelled 意图不产条目但要占号，否则取消后剩余实例与 pred 侧编号错位）。cancel 定位优先级：id 直达 > 话语时段文本匹配 > 序数（对齐 agent 上轮话术枚举序）。

### 6.3 实例化的四条 key 路径都要过同一道检查（最贵的教训）

pipeline 里 key 的产生路径有四条：new 段、归并段、更新段、空 delta 沿用段——**每一条"从合并 final 推导 key"的代码都会在实例场景下把 '#2' 推导回 base，触发伪改名**。五跑全量迭代修了四轮：

- run2 −12pp 的次生 bug：修复更新段时用 `_instanced_key` 避让，但"自己的改名目标"被当成已占用 key → 强行编 #N 幻影；
- 空 delta 沿用段（"保留第二份，无修改"）最阴险：k 推导丢后缀 → 伪改名 → `_consumed_key=自己` → 透传层把自己 pop 掉，session 直接灭。

**规律**：修复 bug 时新引入的判定逻辑必须覆盖"目标=自己"的退化场景；每轮修复必须配**全场景离线回归**（本项目最终沉淀 6 个 mock 场景：改名/实例更新/cancel+update 组合/mi_off 原语义/纯复读/补 app 归并），只测修的那个场景等于没测。

### 6.4 触发式规则的"更新 vs 新建"边界必须与模型可见信息对齐

pending_app_rule 三轮文案迭代的本质：规则告诉模型"什么情况下写已有意图 id"，但模型能看到的只有 prompt 里列出的信息。桩列表只含**无 app** 的意图——有 app 但缺参数的意图不在列表里，规则说"补充时写 id"模型也找不到锚（S-000220 失败根因）。v3 文案改成【默认更新，谨慎新建】（拿不准一律按更新，错误代价不对称：误更新丢 1 意图 vs 误新建分裂+传染后续轮）才打通。**给模型的指令必须引用模型实际可见的锚点；引用它看不见的东西（内部状态分类）等于没说**。
