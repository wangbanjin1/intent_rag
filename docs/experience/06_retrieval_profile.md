# 06 检索与用户画像

> 来源：v6.0 消融（检索 +8pp）、v11（选择链）、v14/v15（record 唯一反升现象）、v24.0/v24.1（records[0] 规则）、v24.3/v24.4（候选对照表）

## 1. 检索的价值与双刃性

- 检索 on/off = +8pp（v6.0 @ dataset_2）：in-context demo 是本范式最大的单一正贡献。
- 双刃性：demo 教格式也教坏习惯（v21.0 序数、v12.0 缺头）；**demo 里的每个表述都在教模型一个习惯**。
- query 构成：`prev_state || utterance` 拼接——prev 进 query 让多轮检索偏向前轮意图，id 协议化后 prev_state 文本形态变化 → **embed cache 必须重建**（协议改动的一次性成本，且检索结果会漂移，跨协议归因要注意）。

## 2. 画像指代（"按上次记录"）的完整解法路径

三代方案，一代比一代便宜有效：

| 代 | 方案 | 结果 | 教训 |
|---|---|---|---|
| 1 | 后处理选值（规则补全/加权投票/重注入二次 LLM） | 全部净负 | 选择器看不到 GT；"只补缺失"保护不住重新 validate 的连带破坏；**后处理选值路线整体封死** |
| 2 | 选择链 demo（v11）：对 demo 中 record sourced 字段自动生成"选择链 summary"注入 | +2.87pp | 让模型看到"怎么选"的推理过程，生成侧解决 |
| 3 | 确定性规则（v24.1）：无约束"上次"严格 = records[0]（completed_at 最新），触发式注入字段明细 | +4.97pp | 数据集规则明确后，直接喂答案明细比教推理更强 |

**迁移判断**：指代规则如果可以从数据统计出来（如"上次=最新一条"），直接规则化+喂明细；如果依赖上下文语义（"第N条"），喂候选对照表（v24.3）+ 生成前推理（选择链）。

## 3. 模型行为偏差的实证（画像场景特有）

- **强模型更积极引用画像反而受害**（v14/v15 两次实证 record 错误唯一反升）：模型倾向取画像值被带偏——画像信息是助攻也是污染源，规则要明确"用户明说值优先于画像"。
- 翻转值是多稳定吸引子竞争（profile 习惯值 vs records[0] vs records[1]）：这是投票/重采样在画像场景失效的根因。

## 4. 用户话语↔GT 一致性核查（数据集信任建设）

三路扫描脚本化（tools/_scan_user_wrong.py / _scan_gt_provenance.py）：
- 正向：明说值≠GT 且无改口 → 34 候选全误报（选择疑问设计）；
- 反向：GT 值的话语出处核验 → 0 无出处；
- 应用/服务名出处 → 变体构词可解释。
**结论：数值类字段 GT 可信；record/Memory 类字段的话语出处天然缺失（设计如此），评估时要豁免而非治罪。**

## 5. 检索库工程细节

- build_casebank 必须显式 DST_DATASET（v16 教训：误用默认数据集只建 376 条）；
- embed cache 按模型分文件（32b 独立副本防并行写竞争）；
- 负例 demo（invalid case）与正例一起检索展示（schema 约束教育）；
- 检索 top_k 与多样性（MMR）调参收益远小于 demo 内容正确性。
