# 04 Prompt 工程：demo 纪律、喂信息与规则博弈

> 来源：v12.0→v12.1（demo 格式 ±5pp）、v11（选择链 +2.87pp）、v21.0→v21.1（序数对齐）、v22.0③（always-on 净有害）、v24.0→v24.1（约束识别粒度）、v26.2（身份判定行）

## 1. Demo 是第一公民：逐字节一致纪律

- v12.0：注入的纠正 demo 无 `# intent:` 头 → 模型模仿省略头 → delta 整段丢弃，目标模板 8→0。v12.1 修复（demo 补头）反超 +3.7pp。
- **规则：demo 的输出格式必须与系统要求的目标格式逐字节一致**。每次改输出协议（v26 id 化同理），demo 同步改是第一优先级，不是可选项。
- demo 会被模型模仿的不只是格式：demo 里写了 `records[N]` 序数 → 模型拿序数数画像列表（v21.0 净负根因）。**demo 里的每个表述都在教模型一个习惯**。

## 2. 喂信息 > 讲道理

| 手段 | 形态 | 实测 |
|---|---|---|
| 喂信息 | agent 上轮回复进 prompt（agent_context） | +3.30pp，T3-3 破零（信息不对称是真因） |
| 喂信息 | records[0] 字段明细注入（record_rule） | +4.97pp，项目最大规则收益 |
| 喂信息 | 状态快照（status_prompt） | +1.43pp（强模型更会用；32b 上 +0.71pp 同向） |
| 讲道理 | 改口规则文案（correction_rule） | +0.31pp 微正 |
| 讲道理 | 消歧规则（disambiguation_rule） | +0.62pp，但 v21.0 初版因与模型可见信息结构冲突净负 |
| 讲道理 | record 不超前取值（全局规则） | 净有害回退 |

规律：**信息型注入的收益比约束型高一个量级**。约束型规则的额外风险见 §4。

## 3. 规则注入的工程模式

- **触发式注入**（触发条件命中才把规则段+上下文写进 prompt），不要 always-on：全局规则会扰动非目标类（v22.0③：确认轮丢意图、明说字段留空；v8.0-a 同教训）。
- 规则必须与**模型可见信息结构对齐**：v21.1 教训——规则说"按 agent 话术顺序数序数"，但模型看到的是画像 records 列表（completed_at 降序），两套顺序冲突 → 模型用错。修法是把规则指向的顺序**显式渲染出来**（v24.3 候选对照表："第N条=记录字段明细"），或者引用模型 prompt 里真实存在的对象（v26.2 身份判定行要求对照上面列出的每个 id）。
- 触发识别的粒度决定成败：v24.0 把话语中任何 app 名当筛选条件 → PER 原型零覆盖；v24.1 改"是否紧邻记录指代词" → 破局。**约束识别要在真实错误样本上逐例调**。

## 4. 强制推理行（身份判定/选择链）的双刃性

- 收益：逼模型先看可用选项再做决定（S-000040 型 new 重建被救）；PAR 校验（行数不够重采样）提供形式保证。
- 代价：每段 +1 行 prompt 税（实测 15 个稳对翻转成继承波动）；模型可能"写了正确理由、得出错误结论"（判定行不是逻辑约束）。
- 适用判据：错误样本中"模型没看可用选项就行动"的比例高 → 值得；错误是纯值波动 → 加行只是加税。

## 5. 状态快照与上下文

- status_prompt（意图状态快照进 prompt）：强模型受益（plus +1.43pp），弱模型几乎无效（32b +0.71pp）——**上下文利用能力是模型能力的一部分**，跨模型消融才能发现。
- agent_context（上轮 agent 话术）：治信息不对称的典范——T3-3 全灭不是模型不会消歧，是它看不到 agent 列的候选。**先问"模型到底看得到什么"，再问"模型为什么错"**。

## 6. 长度税

prompt 每加一段都有代价：v16.0 status_prompt 的时间推算 +5、v26.2b 的 15 个继承波动翻转。预算意识：**每加一段规则/上下文，都要在翻转归因里专门检查"非目标类的回归"**。

**v27.0 对冲范例**：新机制落地时同步压缩被取代的旧散文段——日期表注入后，prompt 里"明天=ref+1、后天=ref+2"等文字算术规则和冗长例题使命已完成，压缩后系统 prompt 净 **−840 字符**（9924→9084），变长税变净收益。"加一段换两段"应成为注入类机制的标准动作。

## 7. 增补（v26.3，2026-09-15）：规则文案的三轮迭代 = 边界对齐的三次校准

pending_app_rule 三版文案的收益轨迹（85.47% → 85.47% → 88.46%），每版的差异只是一段话：

- v1："app 未明说不得猜"+桩列表 → S-000184 副作用：**更新段**的 app 也被留空丢失（规则说"留空"，模型理解为"全部留空"）。
- v2：+更新段 app 必须 coreference 沿用 → 暴露 S-000220：补参数轮模型找不到更新锚（I1 有 app 不在桩列表）→ 误判新建。
- v3：【默认更新，谨慎新建】+ 拿不准一律按更新 + 仅"新服务词+新时段且与所有已有意图都对不上"才 new → 转正。

三条结构化教训：
1. **规则条款必须覆盖"该规则适用的全部段类型"**（新建段/更新段/沿用段），只写给一个类型的规则会被模型泛化到其他类型（v1 的"留空"被泛化到更新段）。
2. **默认值要往错误代价小的方向偏**：误更新丢 1 意图 vs 误新建分裂+传染后续轮——"拿不准一律按更新"把模型的犹豫收敛到低代价侧。
3. **禁止性规则（不许猜）比指令性规则（必须对齐）好执行**：v3 的核心其实只有一条硬禁止（不许从 records/矩阵/schema 猜 app）+ 一个安全默认（拿不准就更新），其余全是边界说明。

## 8. 增补（v27.0，2026-09-20）：四条时间口径规则的注入文案要点

与 v26.3 pending_app_rule 同源的第四轮实战校准（终版采纳：session 92.74%/turn 93.54%，详见 09/11 两篇），特殊之处在**规则间交互**：

1. **矛盾规则必须写清"录什么"**："照字面录入明说值，禁止调和/翻转/倒推覆盖，等待用户后续更正"——初版只说"保字面"，模型仍自行倒推 duration。负面清单（禁止 X）+ 正面默认（录字面值）+ 边界（等待更正）三要素齐才稳。
2. **规则间乘性放大**：提取器错值 → 矛盾检测误触发 → 模型按规则照抄错值，一层错被两层规则背书。**任何"检测到 X 就指示模型做 Y"的规则，检测器精度必须独立验证到 99%+ 才能上线**（v27 提取器 GT 一致率 99.4% 是放行门槛）。
3. **与既有 MUST 条款显式互斥**：新规则与系统 prompt 既有硬约束冲突时（"MUST 算 start" vs "候选不落槽"），必须在新规则里显式写豁免条款，否则模型在两规则间摇摆。
4. **触发词收窄到与 GT 口径逐例对齐**："时长按平时"不应触发"时段优先"（GT：只说时长取时长）——触发条件过宽的回退（S-000080/125 型）比不触发更糟，因为规则一旦出现就获得"本轮最高优先级"。
