## 二、已被当前实验论证的论文结论（论文 ↔ 我们的实证）

### 2.1 A1：推理/时间/个性化是 LLM 槽位填充最大短板 ↔ 我们的错误分布

**论文结论**：ESF-Bench 上高能力 vs 低延迟模型差距最大的类别是数学（+44%）、时间（+33.2%）、计数（+32%）、相对修正（+54.7%）；最弱类别是推理（高能力组仅 59.4%）与个性化（55.9%）。

**我们的实证（v19.0 @ d5 错误归因）**：
- value 错误 93 例中 **rtt 57** 为最大单字段错——rtt 正是需要从画像 record 取值并做语义对齐的"推理+个性化"型槽位；
- **time 错误 37**——时间跨日推算长期是三大瓶颈之一（v1.0 起即记录"多意图张冠李戴 + 时间跨日推算"）；
- v16.0 status_prompt 消融的代价正是"时间推算 +5（prompt 变长）"——与 A1"推理类最难、prompt 变长先伤推理"的方向一致。

**结论**：A1 的 57 场景分类法中 REA（推理）/COR（修正）/PER（个性化）三类，恰好覆盖我们 err_report 的 top3 错误桶（record 值、时间、改口轮丢字段 ~15 例 resolution None）。论文侧与企业实测完全同向。

### 2.2 A1："部分正确≈没用"，用最终全对指标 ↔ 我们的 session 级严格 JGA 口径

**论文结论**：F-JGA 只评估最终对话状态全部槽位是否全对，因为企业部署中部分解价值有限。

**我们的实证**：v4.0 起用户拍板的双口径中，session 级 = 意图集合严格全等（cancelled/rejected 不算 GT），且 turn 级也按"截止该轮累积 final_state"判定（JGA 语义）。E2 的 Overall（意图+槽位同时全对）同理。我们与 A1/E2 的指标哲学一致，且实践中确实看到 turn 级数字（75.47%）系统性高于 session 级（72.05%）——只看单槽/单轮会高估系统，正是 A1 警告的陷阱。

### 2.3 E1：只建模"状态增量"而非全量状态 ↔ 我们的 Δy 程序段设计

**论文结论**：预实验发现 LLM 难以每轮稳定输出全部活跃槽位值，故沿用 MinTL 思路只生成本回合变化的槽位对，再累积成全局信念状态。

**我们的实证**：RefPyDST 主线即"生成 Δy 程序段 → apply 到 prev_state 得 y_t"，与 E1 结论同源。反向证据也有：v12.0 纠正 demo 失败事件中，demo 输出缺 `# intent:` 头导致无头段 delta 被整段丢弃（72/376 缺头、63 败）——一旦增量段无法归并到正确意图，状态就丢，说明增量机制的正确性完全依赖"段→意图"的对齐，这与 E2 的 CoI 结论互相印证（见 2.5）。

### 2.4 E1：oracle 状态大幅救活对话 ↔ 我们 GT prev_state 与真实透传的差距

**论文结论**：ChatGPT-fs 在 MultiWOZ 上 Success 从 0.44（生成状态）升至 0.68（oracle 状态）——状态跟踪是短板，喂对状态后对话引导能力可观。

**我们的实证**：v4.0 口径实证——旧评估用 GT prev_state 不累积错误时 turn 级 70.50% 偏乐观；改真实透传（误差累积）后 v3.0 仅 47.24% session。GT 态 vs 真实态差 ~23pp，方向与 E1 完全一致："状态一错，下游全错"。这也是 v13.1 agent_context 能 +3.30pp 的底层原因——它修复的正是信息不对称导致的状态错误累积。

### 2.5 E2：显式意图分解（意图链）+ 避免 token 级标注 ↔ text-to-Python 多意图段 + `# intent:` 头事件

**论文结论**：把多意图话语显式拆成"意图:子话语"对（CoI），意图越多收益越大（1→2→3 意图 Overall 增益 1.1%→4.3%→7.8%）；让 LLM 输出实体级结构而非逐 token 标签，规避自回归错位；vanilla SFT 直接标注会崩（MixATIS Overall 47.7）。

**我们的实证**：
- 多意图并发方案A（一次调用多 intent 程序段，`# intent:` 头切分）就是 CoI 的代码化实现；
- **v12.0→v12.1 是最强证据**：v12.0 注入无 intent 头的短 demo，模型模仿省略头 → delta 丢失 → 目标模板砸穿（T2-3 session 8→0）；v12.1 给 `_case_to_program` 补 `# intent:` 头 + 无头段兜底归并后，非首轮无头输出 72/376→2/376，session +3.70pp 创新高。E2 所说"显式意图边界是多意图结构化的关键"在我们这里以失败-修复的完整闭环被论证；
- 避免 token 级标注：我们选择 text-to-Python（结构化程序）而非序列标注/XML，与 E2"实体级输出更稳"同向；消融也证实 XML 不优于 Text-to-Python。

### 2.6 A3：槽位填充远难于意图分类；"错误"常是标注口径/规范问题 ↔ R5 噪声事件

**论文结论**：ChatGPT 意图分类接近有监督（79–84%）但槽位填充 F1 仅 13%；100 个错例中 79% 不是真错——句子歧义或标注规范反直觉。

**我们的实证**：
- 错误结构上：missed intent 36 < value 93 + time 37，意图层错误的绝对数远小于槽位/值层——与 A3"意图易、槽位难"一致；
- **R5 record 噪声事件几乎是 A3"79% 的错误其实合理"的中文客服版复现**：49 个 test session 中，用户说"按上次记录"无歧义时，GT 系统性取 users.jsonl 原始顺序第 1 条，而 harness 给模型看的是 completed_at 降序"最近在前"——模型按"取最近"规则选择完全合理却必错（v12.1 在这 49 个上仅 7/49 巧合命中）。剔除后 v12.1 session 56.0%→62.7%。A3 的教训"评估前先审视标注口径与模型所给信息是否一致"已被我们内化为 find_noise 五规则 + 噪声剔除口径的工作流。

### 2.7 A3：示例更多不一定更好 ↔ 我们三次 demo 注入的教训

**论文结论**：30 示例反而比 20 示例差（prompt 过长所致）；示例主要起"对齐任务格式"作用。

**我们的实证**：v12.0（纠正 demo 格式不一致砸穿目标模板）、v11（选择链 demo 首次显著超基线但收益集中）、PMI_β 重排（数据池小无收益已删）。共同指向：demo/示例的收益取决于**格式对齐与信息增量**，而非数量——与 A3、E1（few-shot 收益递减，上下文存储扩大后无增益）三方正合。

### 2.8 C2：LLM 对输入长度敏感 ↔ status_prompt 变长的代价

**论文结论**：prompt 过长超出 LLM 处理能力导致错误输出（prompt.order 重排变长后降幅最大）。

**我们的实证**：v16.0 status_prompt 消融显示收益 +1.43pp 的同时"代价时间推算 +5（prompt 变长）"——快照信息进 prompt 后，最需要长上下文推理的时间类错误反而增加。方向与 C2 挑战3一致。这提示后续任何 prompt 增量（如 agent_context + status_prompt 叠加）都要盯时间/推理类错误的边际恶化。

### 2.9 A2：约束后处理显著提升精度 ↔ 我们的规则 validator

**论文结论**：GLiNER + 约束 16% 相对提升，GLiNER + 微调 LLM + 约束 34%；约束用于过滤误抽、提升精度。

**我们的实证**：规则 validator（apply Δy → y_t 后校验，8 槽位 + 7 类 invalid_reason 含 unresolved_coreference）就是 A2"约束后处理"层的对应物；v8.0-b 的 `_cancel_check_ok` 校验回路同理。A2 的分层架构（轻量预处理 + 生成模型 + 约束）与我们"检索 + 生成 + 校验"三段式是同构的。

### 2.10 跨论文：模型能力（而非参数量/方法栈）是上限主因 ↔ 我们的模型天梯

**论文侧**：A3（涌现能力只在大模型出现，6.7B 以下零样本近无效）、C2（GPT-4 六项全优）、E2（Instruct 版 > base 版）、A1（高能力组 F-JGA +16.3%）。

**我们的实证**：v14.0 换 qwen-plus 突破"方法栈上限 ~70%"旧判断（+7.92pp）；v18.0 qwen3-235b 反而比 plus 低 7.86pp，"不能用参数量对标"；v17.0 status_prompt 在 32b 上 −0.66pp 微负、在 plus 上 +1.43pp 翻正——**同一个 prompt 机制的收益方向取决于模型能力**，这与 A1"高能力/低延迟组在推理类差距最大"、E1"更强模型更能利用给定状态"完全同构。

## 三、值得参考但尚未验证/可行动的结论

按优先级排序（结合当前 v19.0 错误结构：T3-3 全灭 0/14、record 值 93、time 37、missed 36）：

### 3.1 A1：57 场景分类法作为错误归因与测试清单（优先级：高，零成本）——✅ 已落地（v20.1）
当前 err_report 的错误桶（record/memory/时间/漏意图/值/cancel_wrong）是自定义的。已把 A1 分类法相关子集映射为 `error_report.py` 的**二级标签**（原因维度，与一级"错误位置"桶正交）：REA（时间/推理）、COR（改口覆盖）、SR（取消/重置）、CU（消歧/回应助手提议，T3-3 属此类）、PER（画像/记录引用），并补充三个本项目特有维度：**FMT**（形式差异假错误，A2 宽松匹配思想）、**CTX**（状态沿用失败，E1 状态跟踪短板）、**XFER**（多意图串扰，E2）。

**v20.0 @ d5 实测分布（166 错误 turn）**：PER 52 ＞ REA 39 ＞ INT 26 ＞ CU 25 ＞ CTX 8 ＞ COR 7 ＝ GEN 7 ＞ SR 2；FMT 0、XFER 0。三个直接结论：
1. **PER+REA=91/166（55%）**——过半错误落在 A1 认定的全模型两大最弱类，属能力短板而非可修 bug，prompt 修订预期应设为"缓解"；
2. **CU 25 例 > T3-3 模板的 14 session**——消歧/选择类表达散布在其他模板，修补②（消歧候选注入 prompt）受益面比单看 T3-3 更大，首要地位再获强化（T3-3 全灭主因是信息不对称的论证见 §2.1 与 CHANGELOG v13.1）；
3. **FMT 0**——A2 警告的"精确匹配惩罚形式差异"在我们的评估口径下实证为空，§3.4 的宽松匹配参考列优先级下调。

### 3.2 E1：Prompt-recoverable vs Inherent errors 的错误二分法（优先级：高，零成本）
E1 把错误分为"prompt 可恢复"（格式非法、值未规范化——靠 parser/后处理修）与"固有"（幻觉、过度生成——靠模型/示例修）。我们 v5.0/v9.0 两次后处理失败、v11/v12.1 两次生成侧成功，正是这个二分法的实证。建议把该二分写入 report_method.md 的方法论：任何错误先归类"可恢复/固有"，可恢复类走 validator，固有类走生成侧，避免第三次重走"后处理选值"老路。

### 3.3 B6：数据合成/扩充时的混合模式与质量控制流程（优先级：中，触发条件=做数据扩充时）
若后续要合成新的训练/测试话语（如为 dataset_6 扩充多意图样本），B6 给出三条可直接搬用的纪律：
1. 不要用单一连接词拼接（MixX 的 4 种连词让模型学会"数连词猜意图数"，换分布即崩 −40%）；要覆盖省略/共指/动名词等隐式模式——我们 d5 已有的"第二条吧""还是刚才那个"正是隐式模式，新合成数据应对齐这类分布而非 and 拼接；
2. 相似度选择源话语（SBERT τ=0.7）把 LLM 合并错误率从 16~41% 降到 9~14%；
3. 三指标（词数/连词/代词变化）+ 人工审查的过滤流程。
注意：B6 也实证了"ChatGPT 即便明确要求避免 'and' 仍 40–72% 用它"——用 LLM 合成数据必须强约束+后过滤，不能信任一次性生成。

### 3.4 A2：宽松匹配 + ITN 的评估补充口径（优先级：低——v20.1 实证 FMT=0）
我们的 JGA 是精确匹配。A2 指出 exact match 会惩罚语义正确但形式不同的输出（"7:00 PM" vs "7 PM"），建议宽松匹配 + 逆文本归一化。v20.1 已在 error_report 二级标签中内置轻量归一检测（FMT 标签：大小写/空格/数值等价后 GT==pred 即标假错误），**v20.0 @ d5 实测 FMT=0**——我们的字段取值（枚举画质/数值 rtt/ISO 时间）形式高度规整，A2 警告的口径问题在本任务不存在。该参考项降级为"已证伪，无需行动"。

### 3.5 C4：不确定性路由作为成本治理预案（优先级：低-中，触发条件=调用成本/延迟成为约束时）
当前每轮一次 qwen-plus 调用，成本可控。若未来流量放大或需换更小模型降本，UDRIL 的"轻量分类器快路径 + 不确定样本升级 LLM"是成熟范式，且其"正负翻倍构造 OOS 信号无需 OOS 标注"的技巧可用于我们域外 app（豆瓣/京东等 matrix_out_application）的检测增强。现阶段仅作架构储备，不建议提前实施（我们无分类器阶段，也无 DistilBERT 训练数据）。

### 3.6 A2：黑盒知识蒸馏作为长期降本路线（优先级：低，触发条件=需要私有化/小模型部署时）
A2 实证 70B+ 老师标注 + Llama3-8B 学生微调可得 +25% F1，且"仅 LLM 标注"优于"仅人工标注"、人工对齐仅 +1%。若未来需要从 API 模型迁移到自部署小模型，这条路线有明确背书；且我们已有 490 条 train case bank + 全套评估 harness，天然是蒸馏数据的生成与验证基础设施。当前 API 范式下不行动。

## 四、不符合当前现状 / 不适用的结论

### 4.1 C2 主结论"LLM 不适合做 OOD 意图检测"——不适用
C2 的场景是开放集分类（N 个 IND 意图 + 自由 OOD），ChatGPT 在 N>30 时 OOD-Recall 骤降。我们的设定是**封闭 schema**：26 app×6 service 合法矩阵，域外 app（豆瓣/京东/知乎/美团）由 validator 规则判 matrix_out_application，"域外意图输出空或 invalid 都算对"。OOD 判定不依赖 LLM 自由分类，而是结构化校验的副产品——C2 的性能悬崖在我们的架构里不存在。可参考的只是其"领域知识冲突"与"长 prompt 敏感"两个挑战描述（后者已论证，见 2.8）。

### 4.2 E1 的绝对数字"LLM 状态跟踪 JGA 仅 0.27、不可靠"——已过时，勿引用作上限论据
E1 测的是 2023 年 GPT-3.5 时代的指令模型 + 刻意不优化的通用 prompt。我们的 turn JGA 75.47%（qwen-plus）远超其数字。E1 对我们的价值在**结构性结论**（增量状态、oracle 态差距、错误二分），而非绝对水平——引用 E1 数字论证"LLM 做 DST 不行"会与我们的实测直接矛盾。

### 4.3 E2/A2/A4 类"微调路线"——当前范式外
E2 的实体槽+CoI 需要 SFT，A2 的蒸馏需要训练学生模型，C4 的 LLM 精炼器需要 LoRA。我们全栈基于 API 模型（qwen-plus/32b）零训练，微调路线的结论只能作为 3.6 的长期储备，不能指导当前 prompt/RAG 层面的迭代。特别地，E2 消融中"vanilla SFT 崩溃"不能外推为"vanilla prompting 崩溃"——零样本大模型 + 检索 + 结构化输出在我们的任务上已被验证可行。

### 4.4 B6 的 MID 检测结论（ChatGPT 在 BlendX 上仅 22–76%）——任务不同，不可对号
B6 是单句多意图**检测**（输出标签集合），我们是多轮多意图 **DST**（输出状态增量）。且 B6 的崩盘主因是训练/测试分布套路不一致，而我们用的是真实数据集（d5 话语全改自真实分布，非拼接合成），不存在"数连词"投机空间。我们的 missed intent 36 例主因也不是连接词模式，而是消歧信息不对称与意图集合完整性（235b 漏意图 83 vs plus 56 的证据）。B6 的数字不应被引用来预测我们的意图识别上限。

### 4.5 A1 的部分场景类——LMV/SC 多数子类不适用
A1 的 LMV（64+ 字符长 ID、多值槽）与 SC 的正则/单位/跨槽约束子类，对应的是 ITSM 表单类 schema；我们只有 8 个槽位、取值多为枚举/时间/数值，无长 ID、无多值槽。A1 对我们的有效子集是 REA/COR/SR/CU/PER 五类（见 3.1），其余场景不必纳入测试清单。

### 4.6 A3 的 ASR 结论——场景外
A3 显示 ASR 转写使意图准确率掉 5–7pp 且 LLM 不能纠正同音错误。我们是纯文本入口，不适用；若未来加语音入口再回看。

## 六、一页纸结论

1. **最该记住的三条已论证结论**：增量状态建模是对的（E1）；显式意图边界（`# intent:` 头）是多意图结构化的生命线（E2/v12 事件）；评估前先审标注口径与模型所见信息的一致性（A3/R5 事件）。
2. **最该行动的两条参考**：把 A1 的 REA/COR/SR/CU/PER 五类映射进 err_report 二级标签；在 error_report 加宽松匹配参考列（A2），量化形式差异造成的"假错误"。
3. **最该避免的两条误用**：不要引用 E1 的 JGA 0.27 或 B6 的 MID 数字作为我们任务的能力上限证据（任务/时代不同）；不要在当前 API 范式下启动任何微调路线（E2/A2/C4），它们是成本/私有化阶段的储备。
4. **预期管理**：record/个性化类（修补③）在 A1 中是全体模型的最弱项，prompt 侧修补设定"缓解"目标；时间/推理类对 prompt 变长最敏感（C2/v16.0），后续 prompt 增量必须带时间类错误的回归监控。
