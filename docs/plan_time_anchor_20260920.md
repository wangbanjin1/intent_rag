# 时间问题解决方案（v26.3-p3 错误驱动）

日期：2026-09-20。数据基础：`eval_dual_v263p3_d6_best_run5`（d6 当前最佳，session 88.03% / turn 89.90%），并对 run1~run5 做跨跑稳定性核查。

> **实施状态（2026-09-20 终版：采纳定案）**：P0+P1-a 已实现并经三轮全量迭代采纳为 v27.0（详见 CHANGELOG v27.0 及 report_experiments §2）：
> - run1（初版）81.20% **−6.8pp 大回退**——区间终点省略时段词被解析成 AM + 误触发矛盾规则让模型照抄错值；
> - 修复（子句级时段继承/跨夜滚动/无锚兜底）→ fix_run1 91.88%（time_wrong 22→4）；
> - fix2 收窄 profile_slot 触发 + 时长候选语境双收 → 91.88%/92.93%；
> - **终版 fix3：session 92.74% (217/234) / turn 93.54% (463/495) / 状态机 86.08%，vs 基线 +4.71pp/+3.64pp（单跑超噪声带 2 倍，用户拍板免双跑）**，time_wrong 19→5；11 个机制性目标 case 8 个 session 转正；回退 6 个经基线五跑稳定性核查确认无机制性回退（S-000246 基线 4/5 败、S-000114 基线 2/5 对，其余错误字段与时间机制无交叠）。**已写入 config_d6_qwen_plus_best.json（六时间开关全开）为 d6 新最佳**。
> - 回放纪律补丁：对照组必须盯 turn 级 time_wrong 增量，不能只看 session 翻转。
> - 未实施：P1-b（跨轮明说时间回填，S-000072 型）；残余报数据侧（S-000066 duration GT 设计字段、画像 3 用户时段/时长不一致、S-000156 OCR 字面口径）。经验沉淀：docs/experience/11_time_rules.md。

## 3. 对方案一/方案二的评估

### 方案一（规则时间提取器）——注入形式可行，后处理形式不可行

**后处理形式（提取后填槽/与 pred 对比纠错覆盖）：不可行，有项目内实证：**
- v23 时间规则移植已封顶层：对已规范化输出的规则恒等失效、回放净负；v9.0 显式选择器证明"validate 后二次干预"副作用 > 收益。
- 本批错误里 GT 口径本身"反规范化"：C 类保字面矛盾、S-000156 保 OCR 字面。后处理把 pred 改"合理"只会离 GT 更远。
- validator._complete_timestamp（知二推一）已覆盖"补缺失"场景，剩余错误是"值错"不是"缺"，后处理无信息优势。

**注入形式（提取+预解析后注入 prompt，让模型引用结论）：可行，且与项目全部成功改动同构**（record_rule / candidate_map / 画质表全是"给预计算结论"模式）：

1. **P0-a 预计算日期表**：每轮无条件注入"今天=X月X日、明天=…、后天=…、大后天=…"（由 reference_time 预生成）。治 A 类（3 session，约 5 turn）。成本约 4 行 prompt，零风险。
2. **P0-b 明说时间预提取**：正则从当前 utterance 提取"X月X号/上午下午晚上凌晨X点[半]/X个小时/从A到B/到B结束"，预解析成绝对时间候选注入（"本轮明说：end=07-22 21:30"）。治 A 残余（凌晨12点）、E 过度留空侧（S-000099）、F（同一提取结果标注多子句共享）、H 算术。提取器宁缺毋滥（低精度模式触发时不注入，不干扰）。
3. **P1-a 口径触发规则**（复用现有 `_is_disambiguation_turn` 式窄触发）：
   - 预解析检出 start>end 或三要素不一致 → 注入"用户表述矛盾，照字面录入，勿调和、勿翻转"（治 C，2 session ×2 turn 全稳）。
   - 检出"按平时…时段/时长"且画像两字段冲突 → 注入"以常用开始时段为准，duration 由时段推"（治 D，3 session 全稳，仅改 prompt 第 129 行措辞即可先验）。
   - 检出"按…记录"且本轮有明说时间 → 注入"时间以本轮明说为准，禁取 record 时间字段"（治 B 的 S-000140）。
   - 检出"或者"+"还没定/先确认"候选模式 → 注入"候选时段不落槽，仅登记无歧义字段"（治 E 的 S-000185）。
4. **P1-b 跨轮明说时间回填**（S-000072 型）：会话级缓存明说时间，新建意图且时间槽空时注入提示。机制复杂，放第二批。

**理论上限估算**：P0+P1-a 命中约 12-13 个机制性 session，session 级 88.03% → 理论 +3~5pp（实际打折，须双跑验证）。触发面全为窄触发，非目标类误伤风险低。

### 方案二（模型改写轮，把时间改写成推理友好格式）——不推荐主线

- 对确定性现象（明天/后天/凌晨12点/时长词）：规则提取严格优于 LLM 改写——零成本、零误差；改写器本身就是会犯 S-000249 那种错的 LLM。
- 对非确定性现象（矛盾口径/候选边界/跨轮归属）：改写器要解决与 DST 完全相同的理解问题，误差只是从 DST 环节上移到改写环节，且多引入一处误差源。
- 成本：每轮多一次 LLM 调用（d6 全量约 500 次/跑），改写质量需独立评估，且改写改变 utterance 分布，可能影响检索/demo 匹配。
- 文献旁证：LLM 日期算术弱是已知系统性缺陷，有效缓解是"预计算注入/工具执行"，不是"再让一个 LLM 做一遍"。
- 若要做，仅作低成本消融对照：仅在检出相对日期词时触发、只替换时间表达式。预期收益 ≤ 方案一注入。

## 4. 论文证据（arXiv 检索 2026-09-20）

- **arXiv:2505.16088**《Date Fragments: A Hidden Bottleneck of Tokenization for Temporal Reasoning》— 日期错误部分源于 BPE 分词割裂，不常见日期掉点达 10pp。→ 模型"会规则但算错日期"有底层机制解释，prompt 文字规则救不了，须给预计算结果。
- **arXiv:2601.07148**《Measuring Iterative Temporal Reasoning with Time Puzzles》— GPT-5 无工具仅 55.3%；**日期以显式形式给出时性能显著提升** → 直接支持 P0-a 预计算日期表。
- **arXiv:2511.09993**《SPAN: Cross-Calendar Temporal Reasoning》— LLM 平均 34.5%，工具增强代码生成 agent 达 95.31% → 时间计算交给确定性代码（本项目 find_timestamp 沙箱已是此形态，错误在参数生成端）。
- **arXiv:2507.06450**《A Semantic Parsing Framework for End-to-End Time Normalization》— 时间归一化框架=LLM 代码生成 + 可执行校验 → 支持"规则提取+执行验证"而非"LLM 自由推算"。
- **arXiv:2505.20243**《It's High Time: A Survey of Temporal Question Answering》(ACL 2026) — 时间表达式归一化综述，规则系统（SUTime/HeidelTime/Duckling 中文可用）在客服这类窄域仍是基线强度方案。

结论一致：**相对时间锚定用确定性规则预计算注入，是文献与项目内实证共同支持的方向；LLM 改写/后处理纠错均非主流且有反例。**

| 批 | 内容 | 预估工作量 | 验证 |

**纪律**（沿用项目口径）：
- 单次 ±2pp 内不作采纳依据，一律双跑取均值；触发式规则必须先离线回放（目标 case 1修0破）再进全量。
- 每条规则单独消融配置，合并版与单开版对照，防 v22.0 式合并归因不清。
- 全量跑三件套：DST_DATASET/--split/--noise_file 同设；完成后 err_report + CHANGELOG + 三册。
- 回退条件：合并版获救/回退比 < 1，或任何单条规则离线回放出现破窗。

## 6. 风险

- P0-b 提取器误报会污染非目标类：必须低精度不注入 + train 集误报率 <2% 门槛。
- C 类"保字面"口径与"关键要求 MUST 算 start"指令存在张力，注入措辞需同时修正第 117-118 行（S-000185 实证该指令过度触发）。
- d6 只有 15 个时间错误 session，绝对量小，任何单条规则收益可能落在噪声带内——以"机制命中 case 离线转正"为主要采纳证据，全量双跑为辅助确认。
