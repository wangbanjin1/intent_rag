# Record 选择器方案（v27.0 错误驱动，2026-09-22）

> **实施结论（2026-09-23，否定关闭）**：三轮全量（EVIDENCE 全注入 81.20% → latest 措辞加固 88.46% → defer-only 89.32%）均净负于 v27.0 的 92.74%。defer 机制在 T3-3 目标家族 5 例机制性转正（悬空口径 + 消歧 4.5 补值端到端工作 ✓），但注入面持续扰动非目标类，扰动面 > 靶区。**路线关闭（record_selector.enabled 默认关，代码留档）**；与 v25.0 反思路线同构教训。**画质表补缺独立采纳**（确定性数据修复，S-000114 必救无扰动）。全文见 CHANGELOG v27.1。

数据基础：`eval_dual_v27_time_fix3.jsonl`（当前最佳 92.74%/93.54%，17 个失败 session）。

## 0. 一句话结论

用户直觉的"添加 record 选择器做额外判断"方向正确，但**形态必须是"生成前的证据注入"而不是"生成后的结果改写"**——后者（v9.0/v10.0 显式选择器、v23 规则后处理）已有三次全量实验证伪。本方案把"该不该取记录、取哪条、该不该等消歧"这三个口径问题在生成前用确定性规则预判，以 RECORD EVIDENCE/RULE 段注入，与 v27.0 时间机制完全同构。

## 1. 错误盘点："record 选错"实际是四种病灶

对 fix3 全部 record 相关错误逐例归因（结合 GT source_ref 反查每字段的真实来源），13 个错误 turn 分四类：

| 病灶 | turn | session | 根因 |
|---|---|---|---|
| **A 画质映射错** | 3 | S-000114/169/026 | prompt 画质映射表条目缺口 + 模型查表遵从错误 |
| **B T3-3 消歧错位** | 5 | S-000056/192 | 客服话术顺序→记录对齐仍靠模型（对照表覆盖率 45%） |
| **C 消歧轮抢跑** | 3 | S-000056/123/192 | 记录指代有歧义时 GT 口径"字段悬空待消歧"，模型提前自行取值 |
| **D 补槽遗漏** | 2 | S-000150/075 | 消歧确定 app 后，画质/时延未从本轮/上轮语境带出 |

关键佐证数据（决定方案形态）：

- **C 类三例的候选检测是确定性的**。S-000123 用户说"查一下7月1号完成的云游戏记录"——按约束过滤画像记录后**恰好 2 条候选**（R-001/R-005）；S-000056"之前会议的历史记录"过滤后 **7 条**；S-000192"最近办过的记录"**无任何筛选条件且共 4 条**。三条全都是"约束无法唯一定位记录"——而 GT 口径正是把字段悬空、由客服在第 2 轮消歧。**"约束过滤后候选数 >1 且话语无序数选择" → 应悬空**，这是纯规则可判的。
- **现有机制在这个断点上缺席**：record_rule（v24.1）对这三例全部**正确地没有触发**（S-000192 命中"办过"预选轮排除；S-000123/056 命中筛选条件排除）——它设计上只管"无约束取最新"，管不了"有约束但约束不唯一该不该等"。悬空口径目前只存在于 prompt 的记录选择规则散文里，模型读过但 T3-3 场景下仍抢跑。
- **A 类中 S-000114 是表缺口实锤**：全库 source_ref 反查，prompt 画质表相对 d6 GT 缺 5 个条目（哔哩哔哩/视频 高清=720p、哔哩哔哩/视频 4K、咪咕/视频 4K、爱奇艺/视频 4K、抖音/看直播 标清），其中 **8 个 test session 用到这 5 个组合**（S-000028/013/062/083/110/130/132/114），目前 7 个侥幸对（默认值恰好一致）、**1 个错（S-000114，缺"高清"条目落默认 540p，真值 720p）**。表条目缺口是确定性数据问题。

## 2. 为什么"生成前"可行而"生成后"已被证伪

v9.0/v10.0（2026-08-18）的失败形态：在 **validate 之后**插入一个选择器，用投票/重注入决定取哪条记录，然后改写已生成的字段——结果是"只补缺失保护不住重新 validate 的连带破坏"，两次全量净负。

本方案的注入形态与之有三个本质区别：

| 维度 | v9.0 后处理选择器（已证伪） | 本方案生成前注入 |
|---|---|---|
| 作用位置 | validate 之后改写 final_state | prompt 组装之前提供证据 |
| 模型角色 | 被剥夺决策（改它的答案） | 保留决策（喂它证据+口径） |
| 失败模式 | 重新 validate 连带破坏时间字段/intent key | 最坏情况 = 回到无注入现状（宁缺毋滥则不注入） |
| 决策依据 | 投票/众数（看不到口径） | 数据口径规则（悬空/最新/消歧，已逐例核验） |

论文旁证（arXiv 2026-09-22 检索）：实体/记录定位前置是 RAG 领域的成熟结论——ELERAG（2512.05967）在生成前注入实体链接信号、uRAG（2405.00175）把候选结构化后交给下游、"检索先行再生成"显著降低幻觉（2508.01290 处理实体链接失败时的部分知识注入，对应本方案的悬空回退）。方向一致：**定位与生成解耦，生成器只做最后一步**。

## 3. 组件设计

### 组件 ①：记录悬空/定位预判（record_selector，治 C + 强化 B 的地基）

新函数 `record_evidence(utterance, user_context) -> RecordEvidence`，在 pipeline 触发规则区（与 record_rule 相邻）运行：

```
判定树（全部确定性）:
1. 话语无记录指代词（记录|历史|上次|之前|最近…办过） → 不产出（不注入）
2. 提取筛选条件（复用 _record_constraint_hit 的结构: app/service/日期/序数）:
   a. 有序数选择（"第N条"）且 prev_states 非空 → 消歧选择轮，不产出（disambiguation_rule 已覆盖）
   b. 有筛选条件 → 按条件过滤画像 records:
        - 唯一命中 → RECORD EVIDENCE: "约束定位唯一: records[i]=<字段明细>, 被指代字段取其值"
        - 多命中   → RECORD RULE(悬空): "约束命中 N 条, 无法唯一定位, 按口径被指代字段
                     本轮留空(等待客服消歧), 禁止提前取值; summary 写明悬空待消歧"
        - 零命中   → RECORD RULE(悬空) 同上
   c. 无筛选条件 → 看 records 总数:
        - 1 条     → RECORD EVIDENCE: "唯一记录: records[0]=<明细>"（强化现有 record_rule）
        - 多条     → RECORD RULE(悬空): 同上（"最近办过的记录"多候选即此例）
3. prev 非空且指代沿用旧值（跟上次一样）→ 不产出（coreference 已覆盖）
```

注入文案示例（S-000123 t1 场景）：

```
# === RECORD RULE (记录指代存在歧义, 本轮生效, 优先级最高) ===
# 系统按用户条件("7月1号完成的云游戏记录")过滤画像记录: 命中 2 条(R-001/R-005), 无法唯一定位。
# 按口径: 被指代字段(rtt)本轮【留空】, 等待客服列出候选后用户选择, 禁止提前从任何记录取值;
# # summary 必须写明"记录字段悬空待消歧"。
```

**对抗性分析（会不会误伤现有正确 case）**：
- 与 record_rule（取最新）互斥：record_rule 触发条件 = 无筛选 + （当前实现为多记录时不触发其排除逻辑）——需调整二者触发域为互补：record_rule 管"无筛选且取最新合法"的会话形态（T1-4 的"按平时"走 profile 不受影响），悬空规则管"约束不唯一"。实现上让组件①先跑，产出 EVIDENCE/RULE 时 record_rule 跳过。
- T3-3 预选轮（"参考最近办过的记录"查询式）已有排除（`选中|办过|参考|查`），悬空规则必须**继承同一排除表**再加自己的判定——S-000192 实测"办过"在排除表内，避免双注入。
- 消歧轮（t2 选择"第N条"）由 disambiguation_rule 接管，悬空规则在检测到序数时静默退出，二者无缝衔接。

### 组件 ②：画质映射表补缺（quality_map 补全，治 A）

**这不是新机制，是数据修复**。做法：从全库（d5+d6 全部 sessions，不止 train）扫描 `source_ref=resolution_quality_map:app:svc:词`，还原完整映射表，与现表 diff 后**只补缺失条目、绝不覆盖已有条目**（避免 d5/d6 两代约定冲突），补前对每条新条目跑 GT 一致性校验（该组合在全部出现过的 session 中 GT 值唯一才收）。

当前缺口 5 条（哔哩哔哩/视频 高清=720p、哔哩哔哩/视频 4K=2160p、咪咕/视频 4K=2160p、爱奇艺/视频 4K=2160p、抖音/看直播 标清=540p），影响 8 个 test session，当前仅 S-000114 错（其余 7 个是默认值恰好一致）——**这是把"侥幸对"变成"必然对"**，防御性收益。

顺带修 S-000169 型遵从错误：话语含画质词且 (app,svc) 在表内时，把该条目**单独**提示注入（"高清@芒果TV/视频=720p，勿用默认"）——一行触发式提醒，与表共存。

### 组件 ③：消歧对照表扩覆盖（治 B，既有立项的推进）

v26.2c 已立项（解析器覆盖率 45%，d6 话术变体超 d5 时代规则）。本方案将其纳入同一优先级推进：补充日期式枚举（"7月18日还是7月11日"）、非标准枚举（"则"、"另外那条"）等变体的解析规则；解析仍失败则安全回退纯文字规则（现状）。此项工作量最大、收益最不确定，**排在①②之后视结果决定是否投入**。

### 组件 ④（D 病灶，暂缓）

补槽遗漏（消歧后带出画质/时延）与 pending_app_rule 同族（"默认沿用已有语境"），当前 2 turn 且与 X-2 实例边界交织，**本轮不动**，待①②落地后看残余。

## 5. 风险与边界

1. **悬空口径的适用面**：三例全部在 T3-3（查询→消歧模板）。T1-4"按平时常用的"走 profile 不含 records；T2-x"按上次记录"若约束不唯一在 d6 是否同样悬空**未逐一核验**——实现前先对 d6 全量做一次"约束不唯一且 GT 取值"的扫描，若发现 GT 直接取某条的 case，则悬空规则需加"仅消歧类会话（session_meta 有 Request_Disambiguation 信号）才悬空"的限定。
2. **与 record_rule 的触发域划分**是最大的工程风险（二者抢触发会双注入互斥规则），实现时组件①为唯一入口、record_rule 降级为其子分支。
3. 组件③解析器扩充本质是"追着话术变体打补丁"，天花板有限——若①②落地后 T3-3 仍是最大洼地，更根本的解法可能是**客服话术侧也做结构化预解析**（把候选对照从"解析自然语言"改为"生成期同时输出结构化候选"），但这需要动数据生成侧，超出本轮范围。
