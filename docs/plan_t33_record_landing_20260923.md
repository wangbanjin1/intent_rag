# T3-3 查询-选择-落地链路修正方案（2026-09-23，v27.0 错误驱动）

数据基础: eval_dual_v27_time_fix3（92.74%），T3-3 模板 2/10（最差洼地）。

## 1. 用户判断确认 + 根因修正

用户观察"模型无法列举所有满足条件的记录→选择链断→整 case 挂"。经逐例核对（10 个 T3-3 全量）:

**事实修正**: 客服话术只列举部分候选（如 S-000192 客服列 3 条、画像有 4 条；S-000056 客服按日期归并列 3 条、画像 7 条），但 GT 选择基准 = **客服话术序**（v21.1 已实证 100%），模型无需枚举画像全量——列举缺口不直接致命。

**真正根因（GT 口径逐例核验）**: T3-3 的 GT 语义是三段式:
- t1（查询轮）: 用户明说字段落地（如时间），记录指代字段**悬空**（app/svc/res/rtt 全空桩）
- t2（选择轮）: 选定记录的 **app/svc/res/rtt 全量落地**（source_type=Record，source_ref=记录id）
- t3（确认轮）: 状态 Confirmed

模型失败 = 消歧规则第 1 条 **"不得新建 intent 段: 候选记录中的 app/service 禁止用作输出"** 与 T3-3 语义**正好相反**——该规则为 T2-x 场景设计（防记录 app 误当新意图），但 T3-3 恰恰要求选中记录的 app/svc 落地为保障身份。6/10 失败案例（S-000040/072/140/174/246/089）t2/t3 全挂于此：模型输出 `# intent: none` 或只补 rtt，app 全链断裂。

次要病灶: ①t1 抢跑（S-000056/123/192，v27.1 defer 机制已能修——run3 中 S-000123/192 已转正）②记录值溢出（S-000192 t2 把选中记录 720p 覆盖用户明说 540P——消歧规则第 4 条"只取需要的字段"未区分明说/悬空）③记录时间污染（S-000089 t3 用记录 completed_at 05:25 当保障时间，GT=用户明说 7月14日 3-4 点）。

## 2. 方案（记录模块化 + 语义分支）

用户提议"record 选取全部提成模块"。结合 v27.1 教训（注入对抗已验证行为面会净负），本方案**只动消歧会话（T3-3 信号域）**，非消歧轮 prompt 逐字节不变:

### 组件 ①: 消歧规则语义分支（核心，治身份断裂 6 例）
DISAMBIGUATION RULE 按桩意图状态分支渲染:
- 存在空 app 桩（I1 无 application_name，即 t1 悬空桩）→ 段头写桩 id，**规则 1 改写**: "选定记录的 application_name/service_name/resolution/rtt 必须全部落地到该意图（这是记录的全部用途），时间等 t1 明说字段保持不变"
- prev 无任何意图 → 段头写 new，同样全量落地
- 非空桩（T2-x 补槽型，现行为保留）→ 原规则 1/4/4.5 不变
### 组件 ②: 明说优先显式化（治溢出/时间污染 2 例）
消歧规则追加: "用户在前几轮明说的字段值（如清晰度 540P、时间）优先于记录值——记录只填此前悬空的字段，禁止覆盖明说值; 记录的 completed_at 是记录完成时间不是保障时间"
### 组件 ③: 悬空 defer（v27.1 已实现，保留）
T3-3 t1 查询轮约束不唯一 → 记录字段留空待消歧。run3 已证转正。
