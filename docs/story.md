## 0. 任务定义与系统形态（30 秒版）

**任务**：网络质量保障客服的多轮对话状态跟踪（DST）。用户向客服申请"某应用某业务的网络质量保障"，每份保障包含 7 个字段：应用名、服务名、画质、时延、开始时间、结束时间、时长。

**难点**在于多轮交互的结构性复杂度。单句理解并不困难，但真实对话中：
- 用户一句话里可能**同时**申请两份保障（多意图并发）；
- 用户会说"时延**按上次记录**"（指向用户历史档案的指代消解）；
- 用户会在第 2 轮**改口**（"不是云游戏，是视频通话"）、第 3 轮**取消其中一份**（"撤销第一个"）；
- 用户说话本身有矛盾（"9 点开始、8 点半结束"），标准答案的口径是**照字面记录、等用户自己更正**；
- 客服与用户之间的对话（澄清、消歧问句）**模型看不到**，但答案藏在里面。

系统需要在每一轮把这些信息准确写进状态账本并全程累积，最终与标准答案账本做 7 字段严格比对（JGA，Joint Goal Accuracy）。

**系统主干**：每一轮，把用户话语连同历史状态交给大语言模型，模型输出一段操作状态对象的 Python 程序（表达"本轮要改什么"），受限沙箱执行得到增量 Δy，合并进各意图的状态后透传给下一轮。

## 1. 基座：让模型写代码而不是填表格（v1.0，Text-to-Python）

**问题背景**：让 LLM 直接以 JSON 形式输出参数，存在一个无法绕过的缺陷——**指代无法表达**。用户说"时延跟上次一样"，模型只能凭空编一个数值填进 JSON，因为它没有语法手段表达"引用旧值"。

**方案**：采用 RefPyDST（arXiv:2307.01453）的 Text-to-Python 范式。模型输出的不是数据，而是一段操作状态对象的程序，由受限沙箱执行：

```python
# 用户说"时延跟上次一样" → 模型输出：
state.rtt = state.rtt        # 自引用 = 沿用旧值，沙箱执行时自动解析为上一轮的实际值

# 用户说"开始时间不变，时长改半小时" → 模型输出：
state.timestamp = find_timestamp(start=state.start_timestamp, duration="30min")
```

**设计权衡**：`state.rtt = state.rtt` 的自引用在语义上**精确表达了"沿用"**，模型不需要猜测也不需要编造数值；同时程序是可执行的，格式违规、非法引用在沙箱层直接暴露，天然构成一道校验防线。此外，"已知三个时间字段中的两个推导第三个"（知二推一）这类规则，在代码沙箱里是一段可复用的确定性函数，而非依赖模型自觉的口头约定。

**结果**：系统在该范式上跑通。这一步本身不产生分数，但它是后续全部机制的地基——此后两年内的所有改进（检索、规则注入、身份协议、时间证据）都以"往这套程序生成流程里增加输入信息或输出校验"的方式实现，从未推翻重来。

## 2. 检索增强：用已验证的案例示范格式与解法（v6.0，+8pp）

**问题背景**：模型对"如何拆分应用名与服务名""如何表达画像指代"有自己的习惯，未必与标注口径一致；纯指令约束的遵从率有限。

**方案**：将训练集中经人工确认的案例建成向量检索库（embedding + MMR 多样性选例）。每轮以"当前话语 + 当前状态"为查询，取最相似的若干案例，连同其**正确的程序输出**一并放入 prompt 作为示范。

**设计要点**：示范的选择带多样性约束（MMR），避免四个示范全是同一模板导致模型过度模仿单一模式；示范中包含少量**错误案例**（含 invalid 标注），用于教育模型哪些组合会被校验器拒绝。

**形象地说**：让模型做题前先看几道同类型的标准解答——拆分习惯、指代写法、时间格式全都有样可学，而不是凭指令凭空约定。

**结果**：检索开启/关闭的消融实验 = 68% / 60%，**+8pp**，是项目最大的单一基建收益。此后所有输出协议变更（如 v26 的身份协议）都必须同步重渲染检索库示范——示范与目标格式不一致会反向教学（见第 11 节 v12.0 的教训）。

## 3. 强制"先陈述证据，再给结论"：PAR 段（v2.0）

**问题背景**：模型在处理"按上次记录""按平时习惯"这类画像指代时，经常**跳过选择过程直接输出结果**——没说从哪条记录取的值，取错了也无法定位。

**方案**：采用 S3-DST（arXiv:2309.08827）的 Pre-Analytical Recollection 机制：每个意图段的程序输出前，强制先写一行 `# summary:`，内容为"取什么字段、候选有哪几条、选了第几条、理由是什么"。缺失该行由校验回路检测并触发一次重采样。

**设计要点**：这一机制的本质是把模型的**隐式决策显式化**。实测发现，模型一旦被迫先写出"用户要时延→画像有 3 条记录→过滤 service=云游戏→取最近一条=咪咕/20ms"，后续代码抄错值、漏取值的概率显著下降——书写过程本身约束了后续生成。该模式（"强制写出生成前理由"）后来被反复复用：v26.2b 的身份判定行、v21 的消歧选择说明，都是同一思想在不同环节的应用。

**结果**：首轮画像指代全空输出的问题被治住；更重要的是确立了项目的一个通用方法论——**与其指望模型"心里想对"，不如强制它"写出来"**。

## 4. 取消意图：让账本支持"划账"（v4.0，+8.59pp）

**问题背景**：用户说"把爱奇艺那份保障取消"。早期系统的状态账本只能新增和修改，没有删除语义——被取消的意图继续挂在账上参与后续比对，评估必然出错。

**方案**：模型可输出专门的取消段 `# cancel: 爱奇艺/看直播`；沙箱执行时将其转成删除信号，该意图从状态账本及后续所有轮次的透传中移除。

**结果**：session 47.24% → 55.83%（**+8.59pp**，取消场景 0/16 → 7/16）。配套的评估口径修正（v17.1）在 turn 级追加了 +5.83pp（见第 12 节）——机制与口径两步合计，取消场景从全错变为基本全对（后期统计中取消判错仅剩 1~2 例）。

## 5. 模型更换：方法栈收益的总兑现（v14.0，+7.92pp）

**发现**：在完全相同的代码与配置下，仅将 LLM 从开源 qwen3-32B 更换为 qwen-plus，session 正确率 66.01% → 73.93%（**+7.92pp**）——单次换模型的收益超过了此前所有 prompt 优化工作的总和。

**这一步确立了两条项目准则**：

1. **方法栈的天花板主要由模型能力决定**。此前多个"模型能力短板"的结论（如画像指代取值不稳定），换模型后部分自动消失——它们是弱模型在特定机制下的表现，而非任务本质困难。
2. **每次更换模型必须全量重跑所有机制的消融**。后续 v26.2c 的四模型对照（plus / qwen3.8-27b / 235b / 32b）证实："给信息"类机制的收益与模型能力正相关（强模型更会利用状态快照与上下文），而部分约束类机制对弱模型反而更有价值。机制的有效性不是普适常数，是（机制 × 模型）的函数。

**结果**：d5 数据集上四模型对照（同配置双跑）：qwen3.8-27b 89.91% > qwen-plus 88.67% > qwen3-235b 82.61% > qwen3-32b 73.29%。中型指令特化模型（27B）在良好的 harness 配合下可以反超闭源大模型——这个结论直接影响了后续的模型选型与成本结构。

## 6. 三次"账本本身有缺陷"的修复（v25.2 / v26.2b / v26.3-p3）

这一组改动的共同特征：**模型的输出在语义上是正确的，是系统记账结构把正确结果记成了错误**。修复全部在 harness 侧（不修改 prompt、不更换模型），且每一项都先通过错误样本逐例归因确认了因果链。

### 6.1 改口导致账目断裂（v25.2，+6.52pp）

**问题**：状态账本以"应用名/服务名"字符串作为意图的唯一标识。考虑多轮场景：第 1 轮办理"网易云游戏/云游戏"，第 2 轮用户改口"不是云游戏，是视频通话"。模型输出正确（服务名更新为视频通话），但账本按内容字符串索引——服务名一变，系统判定这是**一个新意图**，与旧意图并存：旧账户残留为幽灵，新账户字段残缺。

**方案**（三处统一修改）：
- 意图标识改从**合并后的完整状态**推导（状态 = 上一轮状态 + 本轮增量），而非仅从本轮增量推导；
- 建立归并链：本轮输出若能唯一对齐某个既有意图（如同应用名下唯一的服务变更），执行**原地更名**而非新开户；
- 被更名替换的旧标识进入退役名单，从透传状态中移除，防止幽灵残留。

**形象地说**：银行客户更换手机号，正确业务动作是更新原账户的资料，而不是销户再开一个新客户——后者会留下一个查无此人的幽灵账户。

**结果**：d5 双跑均值 session 80.75% → 87.27%（**+6.52pp**）；"漏识别意图"类错误 34 → 21（其中 21 例深挖后证实大半是本缺陷的假象而非真漏），幽灵意图 26 → 0。**方法论教训（已写入经验库）**：模型行为异常时，先排查 harness 的引用解析、状态合并、生命周期管理，再归因于模型能力——v24.1 时代被归因为"能力短板"的错误，有相当比例是结构缺陷的假象。

### 6.2 意图身份协议：从"靠名字认人"到"靠证件认人"（v26.2b，+1.39pp）

**问题**：6.1 修复后仍存在边界情况——系统通过内容字符串**猜测**模型指的哪个意图，猜测逻辑总有覆盖不到的分支（改口、补槽、消歧选错记录各有不同的失败形态）。

**方案**：为每个意图分配**不随内容变化的稳定标识**（I1、I2……）。Prompt 中按 id 逐行列出所有在办意图；模型输出段头直接写 id（`# intent: I1`）而非内容名；改名（改口）走账本更名通道，id 永不变。为防止模型格式遵从但语义错位，配置三层兜底：新建段的归并校验（两级信号判断是否该写 new 而写了）、取消段强制写名字（名字可自校验）、全场段去重。

**过程记录**：裸 id 协议第一版（v26.0）双跑净负 −3.11pp——模型 100% 按格式写了 id，但"补全型共指"（该写 I1 却写 new 让系统猜）的语义错误率上升。随后三轮"翻转归因→补丁"迭代（v26.1 归并校验、v26.2 身份判定强制行、v26.2b 段去重）逐项修复，最终双跑 88.67%/88.83% 采纳。**教训：遵从率 ≠ 语义正确率；协议必须与 harness 兜底配套，不能裸奔。**

**结果**：d5 时代最佳（88.67%/88.83%），并成为后续所有机制（实例化、时间注入）的载体。

### 6.3 同名多意图实例化：一个钥匙挂两把锁（v26.3-p3）

**问题**：用户完全可能合法地同时持有两份同应用同服务的保障（"再给抖音**加一份**看直播保障，时段错开半小时"）。账本以"抖音/看直播"为键的字典结构下，第二份**直接覆盖第一份**——数据丢失，且评估侧标准答案按同样结构存储，两侧同时塌缩，错误被系统性掩盖（6 个受影响 session 中 5 个因塌缩巧合"判对"，1 个全错）。

**方案**：实例化键——同 base 键的第二份保障自动获得内部后缀（`抖音/看直播#2`），两份各自独立记账与判分；"撤销第一个"类指令支持三级消歧（写 id > 写时段 > 写序数）精确定位操作对象。

**过程记录**：此改动经历五轮全量验证迭代——四条记账路径（新建/更名/归并/空更新）各自暴露过一个专属 bug，其中一轮修复引入的次生缺陷使分数骤降 12pp（更名误判触发自我吞并），靠全场景离线回归测试定位修复。**教训：涉及状态生命周期的改动，每轮修复必须配全场景离线回归，次生缺陷比原始缺陷破坏力更大。**

**结果**：6 个受影响 session 全部干净判分；总分与之前持平（88.03%），但判分语义发生质变——之前被塌缩掩盖的真实模型错误（某第二份保障的画质映射错误在五个运行中始终存在却从未被判错）开始如实计入。**采纳依据是判分诚实度而非总分**。

## 7. 画像指代：把"查档案的结论"直接喂给模型（v24.1，+4.97pp）

**问题背景**：用户常说"时延按上次记录来"。画像档案中有多条历史保障记录，系统按"最新在前"排序呈现给模型；但部分标准答案的记录选取遵循生成期的另一套约定，模型按"取最新"作答在这类场景上系统性失分（历史扫描曾测得此类场景占 test 的 13.9%）。深挖确认：无附加条件的"上次记录"，数据口径 100% 指向最新一条（records[0]）。

**方案**：检测到"按上次记录"且话语中无任何筛选条件（未提应用、日期、序数）时，将最新记录的字段明细直接注入 prompt：

```
# === RECORD RULE (上次记录严格规则, 本轮生效, 优先级最高) ===
# "上次记录" = 画像 records 中 completed_at 最新的一条(即 records[0]):
#   records[0] = application_name=快手, service_name=开直播, rtt=60ms, completed_at=2026-07-20
# 必须遵守:
# 1. 被"上次记录"指代的字段必须取 records[0] 的对应字段值;
# 2. 禁止使用 profile 习惯值或其他记录的字段值代替;
# 3. 用户本轮明确说出的字段(如 app/service/画质/时间)以话语为准, 不要用 records[0] 覆盖。
```

**设计权衡（本机制的精髓）**：不是教模型"如何去档案室检索"（它可能走错柜子、数错序号），而是**系统先检索完毕，把结论连同使用纪律一并交给模型**。模型的职责收窄为"把结论正确地写进对应的槽位"。触发条件经过两轮收窄（v24.0 初版把话语中任何应用名都误判为筛选条件，净负 −2.8pp；v24.1 改为"是否紧邻记录指代词"的结构判断后转正）——**约束识别的粒度决定此类机制的成败**。

**结果**：d5 session 75.16% → 80.12%（**+4.97pp**，当时规则类最大收益）；获救 25 / 回退 9，且 25 个获救中 18 个落在规则触发轮内——因果面干净。**这一"预计算结论注入"模式成为项目最可靠的方法族**，第 9 节的时间机制（v27.0）是其直系延续。

## 8. 消歧场景：让模型看见它本来看不见的对话（v13.1 → v21.1 → v24.4）

**问题背景**：多记录消歧是多轮对话最难的场景。客服问"您是要 A 还是 B？"，用户答"就按第二条"。标准答案取决于 A、B 具体是什么——而这信息在**客服的话术里**。系统原本每轮只喂用户话语，模型对客服侧信息完全不可见，只能瞎猜，该场景（模板 T3-3）长期接近全灭。

**方案（三步递进，每步独立消融验证）**：

1. **信息补全**（v13.1，agent_context）：将客服上一轮回复原文注入 prompt。模型终于"听见了"客服与用户的对话。T3-3 从 0/18 破零到 3/18（**+3.30pp** 广谱收益，T2/T3 多个场景受益）。
2. **规则约束**（v21.1）：仅注入原文还不够——模型会把"第二条"对齐到画像列表的顺序，而客服话术顺序与画像顺序（按完成时间排序）不一致。注入消歧轮规则："候选禁止建成新意图、序数按客服话术列出顺序数、禁止覆盖已有时间字段"。T3-3 → 7/14。
3. **结论对照表**（v24.4，candidate_map）：规则仍要求模型自行做"话术顺序 → 记录字段"的对齐，这一步常出错。系统直接用确定性解析器从客服话术中提取候选列表，生成对照表注入：

```
# 候选顺序对照 (系统已按 agent 话术列出顺序解析好, 直接使用, 禁止自行按 records 顺序重新排序):
#   第一条 = application_name=微信, service_name=视频通话, rtt=50ms
#   第二条 = application_name=腾讯视频, service_name=视频, rtt=80ms
#   第三条 = application_name=淘宝主播, service_name=开直播, rtt=50ms
# 用户说"第N条"即上表第N条
```

**形象地概括三步**：客服与模型之间原本隔着一堵墙——第一步开一扇窗（听到对话），第二步给一副望远镜（规则指路），第三步直接把翻译好的纸条递过去（对照表）。信息传导的每缩短一步，错误率下降一截。

**结果**：d5 上对照表方案打平（−0.62pp，噪声带内，未采纳）；**2026-09-11 在 d6 数据集上转正采纳（+2.99pp，T3-3 turn 从 0.30 升至 0.43、session 从 3/10 升至 5/10，获救 12 / 回退 5 且全部回退无消歧轮——机制零误伤）**。同一机制在两个数据集上的表现差异本身就是泛化性诊断信号：d6 的客服话术变体更丰富，正是对照表最能发挥的环境。

## 9. 时间机制（v27.0，+4.71pp，本周期主战役）

### 9.1 为什么值得专门打一轮

v26.3-p3 定案后的错误报告显示：turn 级错误中**时间类居首**（50 个错误 turn 中占 19 个）；session 级 28 个失败中 13 个由时间字段错误直接导致。对同一配置连续运行五次做稳定性核查，15 个含时间错误的 session 中 11 个**每次运行都错**——这是机制性缺陷，不是采样波动，具备被系统性修复的条件。

### 9.2 先否决两条直觉路线（均有一手实验证据）

| 直觉路线 | 否决证据 |
|---|---|
| **规则后处理**：模型输出后，用规则检测并改写错误的时间值 | v23 全量实测：模型输出格式已相当规范，规则无事可做（回放 1修/0破，恒等失效）；且标准答案口径本身"反规范化"——矛盾保字面、OCR 噪声保字面，后处理把预测改"合理"只会离标准答案更远。v9.0/v10.0 的选择器实验早已证明：validate 之后的二次干预会连带破坏已正确的字段 |
| **LLM 改写轮**：先让另一个模型把话语中的相对时间改写为规范格式 | 改写器与主模型共享同一日期算术弱点（见 9.3 的分词层解释），错误只是从 DST 环节上移到改写环节；每轮额外一次调用增加成本与延迟；改写还会改变话语分布，干扰检索与示范匹配 |

**最终采纳路线**：**规则提取器 + 确定性预解析 + 触发式 prompt 注入**——规则负责计算，模型负责理解与槽位绑定。这与第 7 节的记录规则（v24.1）是同一成功模式在时间域的复用，也与项目此前全部采纳的机制同构。

**论文依据**（arXiv 检索，2026-09-20）：arXiv:2505.16088 证明 LLM 日期算术错误部分源于 BPE 分词对日期字符串的割裂，属表示层缺陷，prompt 文字规则无法根治；arXiv:2601.07148 实测 GPT-5 无工具时间推理仅 55.3%，而**显式提供日期时性能显著提升**；arXiv:2511.09993 显示时间计算交给工具/代码执行可达 95%+（LLM 裸算平均 34.5%）；arXiv:2507.06450 与 arXiv:2505.20243（ACL 2026 综述）支持"LLM 代码生成 + 确定性校验/规则系统"的时间归一化框架。

### 9.3 组件一：预计算日期表（TIME ANCHOR，治"相对日期算错一天"）

**机制**：pipeline 每轮以 reference_time 为锚，预生成日期表注入 prompt（仅当话语含相对日期词时触发，不白耗长度）：

```
# === TIME ANCHOR (本轮日期锚点, 系统已预计算) ===
# 今天=7月22日(周三)、明天=7月23日(周四)、后天=7月24日(周五)、大后天=7月25日(周六)
# 相对日期一律按上表查取, 禁止自行加减天数推算。
```

**实际案例**（S-000249，用户说"后天凌晨4点到上午7点"，参考日 7 月 22 日，"后天"应为 7 月 24 日）：

```
旧版: start/end = 2026年07月25日04时00分 / 07时00分   ✗（模型心算 +3 天，错一天，连错两轮）
v27 : start/end = 2026年07月24日04时00分 / 07时00分   ✓（查表拷贝）
```

**为什么此前的文字规则无效**：prompt 中早已写明"后天 = reference_time + 2 天"，模型理解规则但**算术执行不稳定**——同一段对话中"明天"算对、"后天"算错的案例实际存在。根因在表示层（分词割裂），不是理解层。查表将"+2"这一步在系统侧完成，模型侧只剩字符串拷贝，错误通道被物理消除。

### 9.4 组件二：明说时间预提取（TIME EVIDENCE，"时间提取器"本体）

**机制**：正则模式库扫描当前话语中的时间表达（绝对日期、相对日期、时段词、起止标记、时长短语），预解析为绝对时间候选注入。只提供证据与角色标注，**不做意图归属判断**——哪段话语对应哪个意图，仍由模型决定：

```
# === TIME EVIDENCE (本轮话语明说时间的系统预解析, 直接引用勿重算) ===
#   "后天凌晨4点" -> 2026年07月24日04时00分 [start]
#   "上午7点"     -> 2026年07月24日07时00分 [end]
#   "三个小时"    -> duration=180min
# 组装(一致): start=2026年07月24日04时00分, end=2026年07月24日07时00分, duration=180min
```

**实际案例**（S-000104，"今天晚上11点到明天凌晨12点"）：旧版将"凌晨12点"理解为中午 12:00，推出 13 小时；预解析规则明确"凌晨12点 = 00:00"，v27 正确得出 23:00 → 次日 00:00 的 1 小时。

**多意图边界**：话语含多个意图各自的时段时（"A 保障明天上午10点半结束……B 保障从10点10分到10点40分"），提取器**只列证据、不做组装**——把"哪个时段属于哪个意图"留给模型，因为跨意图绑定需要语义理解，规则硬绑反而会错。

**提取器质量纪律（上线门槛）**：宁缺毋滥——任何一步解析不确定即放弃该条候选，该轮 prompt 与无此机制时逐字节一致。全量扫描提取值与标准答案一致率 **99.4%**（360/362）方予放行；仅有的 2 例外均为数据侧噪声字面（"14时3G分""19点70分"，见第 14 节数据侧清单）。**99%+ 是此类检测器的硬性上线门槛，理由见 9.7。**

### 9.5 组件三：四条口径规则（TIME RULE，治"标准答案与常识相反"的场景）

时间错误中有一类的根源不是模型算错，而是**模型按常识"好心修正"了用户话语，与数据口径冲突**。数据口径为：用户说啥记啥（矛盾值照字面录入，等用户下一轮自己更正）。四条规则各自窄触发、独立消融开关：

| 规则 | 触发场景 | 模型的错误本能 | 注入后的行为 | 实际案例 |
|---|---|---|---|---|
| 矛盾保字面 | 提取器确定性检出 start>end 或三要素互斥 | 自行"纠正"为合理时间（9:00-8:30 → 8:30-9:00） | 照字面录入明说值，等待用户更正 | S-000227"下午3点半开始到3点结束"：旧版调和成 18:30 结束且改口轮继续沿用错误值**连错两轮**；v27 字面录入后两轮全对 |
| 画像时段优先 | 话语含"按平时+时段"且画像两字段数值冲突 | 取了"常用时长" | 以"常用开始时段"跨度为准 | S-000063：画像写时段 10:00-12:00（120min）但时长 90min，旧版取 90min ✗，v27 取 120min ✓ |
| 明说>记录 | 话语含记录指代词且本轮明说了时间 | 把历史记录的时间戳抄进时间槽 | 时间槽以明说为准，记录仅供画质/时延 | S-000140"后天凌晨1点半结束，按最近记录"：旧版抄入记录的 07-07 11:55 ✗ |
| 候选不落槽 | "或者/还是"连接多候选+"还没定/不确定" | 擅自挑选某候选落槽（或因困惑全留空） | 时段留空，仅登记无歧义字段（如明说时长） | S-000185"时间还没定，A方案或者B方案" |

### 9.6 中途翻车的完整记录（run1：−6.8pp，本项目单次最大回退）

**如实汇报**：时间机制第一版上线当天的全量评估为 **81.20%**，低于基线 6.8 个百分点，时间类错误不降反升（19 → 36）。逐案排查显示 30 个回退 session 全部源于**同一个句式**：

> "明天**晚上7点到8点半**"——"8点半"是区间终点，其时段语义由前方的"晚上"覆盖，应为 20:30。初版提取器以单点视角解析，将该"裸时刻"（无自带时段词）判读为上午 8:30。

**连锁放大**（本案例最有价值的部分）：错误预解析值（start=19:00 > end=08:30）反过来触发了"矛盾保字面"规则——prompt 指示模型"照字面录入，禁止调和"，模型忠实执行，**把系统的错误解析值原样抄进了状态**。一条规则的错误输出经另一条规则背书放大，这就是注入机制的**乘性错误**：错误不是加性的叠加，是链式的传导。

**回放为什么没拦住**：上线前的离线回放（11 个目标案例 + 12 个对照）已通过，但两个盲区叠加——目标案例中"区间终点省略时段词"句式仅出现 2 例，覆盖率不足；对照组的判读只看了 session 级对错翻转，而某个对照 session 恰有 time_wrong 0→1 的增量信号被其自身的运行波动掩盖。

**修复**（三处，均在提取器内）：①裸时刻继承**所在子句**最近时段词的语义（混合时段句"晚上7点到8点……上午6点到9点"的第二段正确跟随"上午"）；②跨夜滚动——终点自带"凌晨"或 PM 继承后仍倒挂时滚至次日（"晚上11点到凌晨1点"→ 次日 01:00），真矛盾（如 9:00-8:30，用户口误型）不误滚；③全句无日期锚时的兜底锚定。

**固化为纪律的两条**：
1. 注入类机制的**检测器精度必须独立验证 99%+ 才能上线**（本例的 99.4% 一致率扫描即由此而来，且需覆盖高频句式而非仅目标案例）；
2. **回放必须盯机制桶的增量**（如 time_wrong 计数），不能只看 session 级翻转——总分波动会掩盖机制信号。

## 10. 弱模型适配：把弱模型当作防御缺口的探针（v26.2c）

**发现**：用开源小模型（qwen3-32b/235b、qwen3.8-27b）运行同一套系统时，暴露出一类被强模型"好习惯"掩盖的缺陷——强模型从不写某种形式的坏代码（如全字段自引用沿用不存在的槽位），因此相应缺陷在强模型上永不触发，防御也就从未建立；弱模型则诚实地摔进每一个坑。

**方案**：①沙箱逐行容错——单行引用失败跳过该行、保留已赋值字段，不再整段崩弃；②prompt 增加"只写发生变化的字段"约束（减少无意义自引用）；③非标准输出的防御性丢弃。

**结果**：弱模型提升 +11~+20pp（能力越弱提升越大，235b +20.11pp / 32b +12.11pp / qwen3.8-27b +11.96pp），对 qwen-plus 零回归；最终 **qwen3.8-27b 双跑 89.91% 反超 qwen-plus 的 88.67%**——中型指令特化模型配合完善 harness 可平替闭源大模型，兼具成本与部署灵活性。

**方法论**：强模型会"礼貌地绕过"系统的坑，弱模型会"诚实地踩进每一个坑"。将弱模型作为常规探针纳入开发流程，等于对系统做免费的穷举压力测试；这也是"防御性工程应该在最弱环境下验收"这一通用工程原则的具体体现。

## 10.4 v27.0→v27.2 之间的两轮攻防（时间机制之后，消歧洼地攻坚）

时间机制（v27.0）落地后，错误结构重新洗牌：time_wrong 从首位跌出，**T3-3 消歧（0/10）与 record 选错成为仅剩的两个结构性洼地**。针对它们的攻坚先败后成，两轮攻防的对照构成本周期最有信息量的方法论样本。

**第一轮：record 选择器（v27.1，三轮否定）**——把 v27.0 的成功模式（预判→注入结论）复制到记录指代场景：系统判定"该不该取记录/取哪条/该不该悬空"，以 RECORD EVIDENCE 注入。判定树本身对标准答案行为核验一致率 79/81，但三轮全量 81.20%→88.46%→89.32% 全部低于基线——**判定树越正确，与已有 record_rule 机制的双轨冲突越严重**（模型从两套"正确说法"里自行取舍，行为面被扰动）。三轮迭代（全量注入→措辞加固→defer-only 收窄）都未能把扰动面压到靶区以下，路线关闭。教训：**注入不是加法而是重构**——新机制进入前必须清点它与既有机制共享的行为面，"两套都对"比"一套错"更危险。

**第二轮：候选模式（v27.2，方向反转）**——复盘 v27.1 唯一稳定转正的部分（消歧类 defer 悬空）发现真正的病根不在"怎么选记录"，而在**候选信息从未进入对话流**：T3-3 的正确流程是"t1 列出全部命中候选 → t2 用户选择 → 落地"，但旧规则教模型"候选禁止输出"，模型只能 t1 抢跑建错意图，错误占位把后续轮拖垮（S-000040 三段失效链实证）。修复不是"告诉模型选哪条"（那是 v27.1 的死路），而是**把"列出候选"本身变成模型输出的一部分**——后续客服回复由模型输出驱动的产品形态下，t1 不列候选则下游无从消歧。这正是从"逆行为面注入"转向"顺信息流注入"的转折点。

画质表遵从问题（v27.2.1）也在同期收尾：5 个稳定失败 case 核对发现 prompt 表与数据侧标准表逐条一致（diff=0），错不在表而在**模型对反常识条目（"高清@淘宝看直播=1080p"，高于标清 720p）的查表遵从**。修复 = schema.QUALITY_MAP 标准表 + QUALITY HINT 条目高亮注入——不是改表，是**把模型该看到的那一行放大**。5/5 定点验证转正，与候选模式同族（喂信息而非讲规则）。

## 10.5 候选模式（v27.2，+2.13pp）：把"候选列举"还给模型

（承接 §10.4 第二轮的方向反转）v27.1 失败后复盘 S-000040 发现真正的病根：T3-3 场景的正确流程是"t1 列出全部命中候选 → t2 用户选择 → 按选中记录落地保障"，但旧规则教模型"候选禁止输出"，且模型 t1 会抢跑建错意图，错误占位把后续轮全部拖垮。

修正采用**候选模式**：t1 模型把系统预计算的全部命中记录列为 `# candidate:` 段（旁路记账、不参与判分），t2 用户选定后"解引用"落地（选中候选的身份与参数合并进保障意图），未选候选移除。消歧规则按"意图是否已有身份"分两条路：身份空 → 记录全量落地；身份已有（用户明说过）→ 只补悬空字段、严禁改写身份。

**结果（三跑均值）：session 93.16% / turn 94.75% / 状态机 87.79%（vs v27.0 +0.42pp/+1.21pp），T3-3 消歧家族稳救 4（040/056/174/192 三跑全对）**。双跑曾差 3.42pp，归因 = 消歧规则 1a/1b 分支交模型自判是二义的——修复 = 分支判定上移 harness 侧（桩意图 app 为空与否由系统核验后直接注入分支结论）。这次成功与 v27.1 失败的对照说明：同一类注入，顺信息流方向（把模型该输出的给它输出）有效，逆行为面方向（改写模型已习得的取值习惯）无效。

另一个遗留问题也在 v27.2.1 收尾：三个 session（淘宝看直播"高清"）稳定错在同一处——画质表里"高清=1080p"是反常识条目（高于标清的 720p），模型总倾向落默认 720p。核对发现 prompt 表与数据侧标准表完全一致，错不在表而在**查表遵从**。修复用"条目高亮"：话语提到哪个 app 的哪个画质词，系统就把标准表对应行放大注入。5 个失败 case 定点验证全部转正。方法上与候选模式同族——都是"把模型该看到的正确信息放大"，而不是教它新规则。

## 10.6 候选链路收口（v27.3~v27.3.3，+4.70pp）：从"能列举"到"全链路确定性"

v27.2 采纳后错误分析发现链路仍有断点，四轮修复全部遵循"确定性上移 harness"的既定方向：

**①候选组装并集（v27.3 核心）**：用户约束互相冲突时（"6月29号完成的虎牙记录"——虎牙那条 6月29完成的是钉钉），标准答案恒为两条候选，而旧 selector 用 AND 交集只给 0/1 条 → 候选注入门槛不满足 → 模型自行挑一条落地 → 消歧无解。修复 = 交集≤1 时按"每约束各自命中的最近一条"取并集。

**②选择轮确定性锚点链**：候选明细按客服话术顺序注入（实测 records 降序与话术顺序可能相反，S-000157 实证）、用户"选第N条"由正则确定性解析（13/13 话术全过）、选中记录直接明示给模型、t1 抢跑占位意图允许改写（1c 分支）、明说时间显式锚定"禁止用记录时间覆盖"、B 型明说场景逐意图直给悬空字段补齐指令。每一条都来自一个具体失败案例的归因，不是预设的设计。

**③时间桩兜底（v27.3.1）**：模型 t1 只列候选段、漏掉承载明说时间的意图段（约 2 成发生率）→ 明说时间"无家可归"。harness 用预解析的 TIME EVIDENCE 补建时间桩。这与 prev_state 兜底、知二推一同性质：harness 代执行模型已认可的机械落地（值就在注入的证据里、模型 summary 也复述过），是"时间提取规则化"的闭环。触发改用四重收窄（列举轮+证据完整+零意图段+话语无新目标 app），B 型明说场景明确排除——防止兜底桩反被选择轮全量落地劫持用户明说的身份。

**④两个新数据集暴露的 harness bug（v27.3.3，dataset_930 泛化测试的意外收获）**：
- **id 协议沙箱 prev 断裂**：id 协议下模型段头写 I1，但沙箱收到的 prev 是内容键（app/svc）——`_match_prev('I1')` 永远失配 → prev 空 → 段内 `state.end_timestamp` 自引用解析失败 → 整段增量静默清零。这个结构性缺陷从 v26.2b 起一直潜伏，被"模型恰好极少写自引用"掩盖；d930 上 qwen3.8-27b 更高频率使用自引用句式（约 2% 轮），T2-2 洼地 63.8% 由此暴露。修复 = 沙箱 prev 挂 id 别名视图，T2-2 立即回升 9pp。**这是"弱模型当探针"方法论第二次兑现**（第一次是 v26.2c 的过度沿用崩溃）。
- **字面省略号崩溃**：模型字面抄注释写 `find_timestamp(start=...)`，Python 里 `...` 是 Ellipsis 对象，一路透传到 json 序列化崩溃（4455 session 推理 13 小时后死在写盘）。修复 = 沙箱层把 Ellipsis 视为缺省。

**结果（d6 四跑定案）：plus 97.86%/97.88%/状态机 91.39%（vs v27.2 +4.70pp/+3.13pp），T3-3 10 例 plus 19/20、qwen3.8-27b 20/20 全对，候选管线自身零稳错（剩余稳错 3 例全在候选链路之外的 X-2/T2-2/T1-3）**。qwen3.8-27b 同栈 96.79%/97.58%，与 plus 差距收窄到 1.07pp/0.30pp，"中型指令特化模型 + 好 harness"平替结论第三次复现。

## 10.7 d930 泛化性攻坚（v27.4~v28.4，2026-10-12~21）：跨代数据集暴露的全面重构

新一代数据集 dataset_930（4455 sessions，2264 用户，16 模板 ×2 生成批次）作为最新泛化测试集。这个周期的问题密度远超以往：**三个 harness 潜伏 bug、一次 13 小时跑批崩溃、话术代差穿透全部正则、候选链路从"规则组装"重构为"LLM 语义判定"**——八轮迭代把泛化集从 91.4%（有效段）推到 **94.60%/95.12%（合并 871 抽样定案）**，q38 反超 plus（平替第三次复现），T3-3 从 55.6% 修复到 68%。

### 10.7.1 跨代数据集当探针：三个 harness 潜伏 bug（v27.4 前奏）

首跑就抓出三个长期潜伏的缺陷，全部是"强模型的好习惯/旧数据集的语料分布"掩盖的：

1. **id 协议沙箱 prev 断裂**（潜伏自 v26.2b）：模型段头写 I1，沙箱收到的 prev 却是内容键——引用解析永远失配，段内 `state.end_timestamp` 自引用失败导致整段增量静默清零。d6 靠"模型极少写自引用"掩盖；qwen3.8-27b 在 d930 上高频使用该句式（约 2% 轮）引爆，T2-2 洼地 63.8%。修复 = 沙箱 prev 挂 id 别名视图，T2-2 立即回升 9pp。
2. **字面省略号崩溃**：模型抄注释写 `find_timestamp(start=...)`，`...` 是 Ellipsis 对象，透传到 json 序列化崩溃——一次 13 小时全量跑死在最后写盘。修复 = 沙箱双层清洗。
3. **话术形态穿透**：svc+日期逗号切开、复合尾句误杀判定——正则维护永远滞后一代。

**方法论升级**：v26.2c 确立"弱模型当探针"，本轮升级为"**跨代数据集当探针**"——换数据集跑全量是成本最低的系统性回归。

### 10.7.2 候选判定从规则到 LLM（方案 B→v27.6→v27.6.1，用户定案"不要纯规则"）

话术代差（"候选N"指称取代"第N条"）让全部选择轮正则失效。用户判定选择环节改走 LLM：`candidate_llm.py` 提供 judge（是否在选择+选中第几条）与话术解析兜底，**只做信息抽取不做状态写**（与 v9.0 后处理、v25.0 反思的封死边界划清）。过程中抓出一个新 bug：**待选择状态生命周期没闭环**——t2 落地后 `_cand_listing` 残留，t3 确认轮"确认，就按这个来"再次触发 judge 被判为选择，模型把正确意图改写成另一条候选。修复 = 选择落地后立即清空。

### 10.7.3 办理语义 vs 引用语义（v28，+1.60pp，本周期核心洞察）

65 例错误报告发现"选对候选但落地范围错"占 58%：用户说"**时延就按候选2**"（**引用语义**——只借一个字段）而 harness 用"桩空=全量落地"（**办理语义**）处理，把一次字段引用扩张成一次完整办理。修复 = judge 升级为**一次调用三枚举**（action/pick/scope），按业界受限枚举 schema 模式锁死输出空间；分支指令由 scope 驱动，取代 1a/1b 硬编码。GT 的 `scope_fields` 是这个隐藏维度的 ground truth。

**经验**：①harness 猜不了的语义问题交给 LLM 受限枚举输出——锁死输出空间而非开放生成；②"办理 vs 引用"是记录消歧的隐藏维度；③每轮修复都可能引入生命周期 bug 或过宽副作用（v27.6.1/v27.7→7.1），定点修复必须配全量回归+正反双例。

### 10.7.4 透传三层缺口收口（v28.2/v28.3，+2.06pp）：修 extractor 必须同步修下游文案

错误报告最大类 T2（16 例，25%）"澄清轮明说字段未透传"，逐层修复：

1. **extractor 层**（v28.2）："应用和时延还没定"的"还没定"限定的是 app/时延而非时间——但槽位白名单只认"(开始|结束)时间"前缀，误判全局未定 → 已明说完整的时间被整体抑制。修法 = 关键词扩展 + 紧邻/隔值/后向三层限定形态判定（S-000185 真候选时段经形态校验保持抑制）。
2. **prompt 层**（v28.3）：extractor 修好了，TIME RULE 旧文案"start/end 一律留空"仍把组装结论压掉（模型 summary 原话"受TIME RULE约束，start/end留空"）——**修了等于没修**。修法 = TIME RULE 文案随组装结果分叉：时间已明说→"照常落地"；时间本身二选一→保留"留空"。

**T2 类 16→3**。教训沉淀为总原则五："修规则必须同步修其下游消费者；抑制类规则写成条件式而非绝对式"。

### 10.7.5 候选列表属性匹配（v28.4）：selector 口径分歧的根治

残余 T8 值错位（1959 型）根因在**列表本身**：画像两条咪咕快游（6/12 的 100ms、7/4 的 80ms）,渲染器候选对挑 6/12 那条,selector"约束+取最近"给了 7/4 → GT 要的值不在模型看到的列表里。渲染器候选组成逐 session 采样、无统一可推断规则（d6 结论复现）。修法（用户定案）= **候选列表组装也改为属性匹配**：规则快路径按"候选N"切段逐段抽属性（app/svc/rtt/res/日期）与 records 精确匹配，全部唯一命中才返回；歧义升级 LLM。全量普查 rule 路径 177/258 精确命中，歧义显式升级不再静默污染。

**方法论闭环**：候选链路的三个语义任务（是否在选择/选中哪条/候选列表组装）全部完成"正则硬编码 → LLM 受限枚举/属性匹配"迁移，规则只留快路径与执行保护——与"计算给规则、理解给模型"自洽：属性匹配是理解，查表落地是计算。

## 11. 明确失败并封死的路线（负结果同样是资产）

**v27.1 record 选择器（2026-09-23，三轮否定，本节最新案例）**：时间机制成功后，用同一模式进攻"record 选错"错误——系统预先判断"该不该取记录、取哪条、该不该等客服消歧"，把结论注入 prompt。判定树本身质量很高（对标准答案行为核验一致率 79/81），目标场景也确实被治住（消歧类 5 例机制性转正）；但三轮全量（81.20% → 88.46% → 89.32%）均低于基线 92.74%。根因不是判定树错，而是**定位类注入与已有的记录规则机制"抢话筒"**——模型原本稳定习得的取值行为被第二种说法重新排列，13 个原本判对的 session 破窗。处置：路线关闭（开关默认关、代码留档），其中画质映射表补缺作为独立数据修复采纳（确定性缺口，无行为面扰动）。此案例补充方法论第 4 条的边界：注入机制的有效性取决于它是否与模型已验证的行为面冲突。

以下路线均有完整全量实验背书，结论写入经验库，防止后续重复投入：

| 路线 | 实验 | 封死原因 |
|---|---|---|
| **后处理改写答案**（规则修正模型输出） | v5.0 / v9.0 / v10.0 / v23 四次独立尝试，全部净负 | validate 之后的二次干预必然连带破坏已正确字段（重新校验、重新合并的副作用无法隔离）。**确立铁律：模型没做对的，必须在生成之前帮它；生成之后改它的答案，代价恒大于收益** |
| **反思/自查回路**（检测可疑输出→回灌重生成→择优） | v25.0 双跑净负（−1.86pp） | 触发 10 例仅采纳 1 例，9/10 模型拒绝修改自己的输出；且本任务的时间错误多为"自洽但错"（推错了但逻辑自洽），无内部矛盾可供检测器捕捉——**靶区结构性太小，机制收益上限低于噪声带** |
| **采样投票**（多次生成取多数/verifier 择优） | v24.5 oracle 上限测算 | 即使每次采样都完美择优，pass@2 理论上限仅 +1.63pp，低于 3pp 投入门控——**数学上不成立，无需再实验** |
| **裸身份协议**（只发 id 不配兜底） | v26.0 双跑 −3.11pp | 格式遵从率 100% ≠ 语义正确率；协议类改动必须与 harness 兜底配套（后经三轮补丁成为采纳版 v26.2b） |
| **always-on 全局规则**（不分场景写进系统 prompt 的禁令） | v22.0③ / v8.0-a | 全局规则扰动非目标场景（确认轮丢意图、明说字段被留空）。**约束类规则必须触发式注入**——只在检测到目标场景的轮次生效，其余轮次 prompt 逐字节不变 |
| **LLM 时间改写轮** | v27.0 形态决策阶段否决（未实验） | 改写器与主模型共享同一日期算术缺陷，误差上移而非消除；见 9.2 |

## 12. 评估口径的三次校准（修正"对"的定义，而非放水）

这三次改动不涉及模型与生成逻辑，修正的是**判分规则中模型系统性吃亏的地方**。每一项都做了反向证伪（把修正关掉，确认分数确实回落、错误确实如预期复现），并配备离线复算工具保证历史数字可换算：

1. **取消计分**（v17.1）：旧口径下，被取消意图的 turn 级标准答案仍记历史状态，模型正确执行删除反而被判"漏做"。修正为取消轮标准答案记"应为空"，正确移除计命中。turn **+5.83pp**，34/34 转正零回退。
2. **改口豁免**（v20.2）："用户说错"场景（T2-3）标准答案按设计记录面错误值；模型正确拒收非法值（留空待更正）反被判错。修正为：拒收 = 命中，或豁免被更正字段后比对其余字段。turn **+2.04pp**，14 转正 / 7 仍错（均为真实错误）。
3. **知二推一对称**（v25.1）：模型侧校验器每轮自动补全时间三字段（已知两个推第三个），标准答案却只在"字面明说"的轮次登记字段——中间轮出现"模型多算而标准答案未记"的假错误。修正 = 判分前将标准答案按与校验器相同的规则补齐（只补缺失、不覆盖）。turn **+1.61pp**，11 例转正零翻错。

**统一原则**：模型侧执行过的每一步确定性推导，判分侧必须执行对称的推导——否则模型越严谨越吃亏，分数衡量的就不是能力而是口径差。三次合计 turn +9.4pp，均不改变 session 级（最终态比对，两侧必齐）。

## 附：方法论四原则（每条均有全量实验背书）

1. **先查系统结构，再归因模型能力**。项目三次最大的规则类收益（v12.1 +3.7pp、v25.2 +6.52pp、v26.2b +1.39pp）全部来自 harness 记账逻辑修复；此前归因为"模型能力短板"的错误有相当比例是引用解析、状态合并、生命周期缺陷的假象。排查顺序：账本结构 → 信息可见性 → 模型能力。
2. **计算交给规则，理解交给模型**。日期算术、格式转换、记录检索等确定性步骤在系统侧预计算，把结论注入 prompt；模型专注语义绑定与槽位归属。让模型做确定性计算是给它挖坑（分词层缺陷有论文实锤）；让规则做语义绑定同样危险（v23 后处理、初版提取器多意图误绑均已证伪）。
3. **喂信息 > 讲道理 > 事后修补**。把模型看不到的信息（客服话术、记录明细、预计算日期表、状态快照）注入 prompt 是最可靠的收益来源；加禁令类约束收益低一个量级且需触发式设计；生成后修改模型输出的路线四次尝试全部净负，已封死。
4. **注入机制的错误是乘性的**。一条规则的错误输出会被另一条规则背书放大（v27 run1：提取器错值 → 矛盾规则指示照抄 → −6.8pp）。因此：检测器精度必须独立验证 99%+ 并覆盖高频句式才能上线；回放必须盯机制桶的计数增量而非仅看总分翻转；任何新规则与既有硬约束的冲突必须显式写豁免条款。
